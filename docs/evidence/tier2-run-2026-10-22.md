## Defect 1 (fixed in the harness): the evaluator cannot read a retried boot

`stages.log` held two boots — the first boot reached multi-user but was rebooted before the
smoke test finished, the second wrote `result.json`. `evaluate.sh` read the file across boots
and reported `HARNESS_ERROR: stage-order-inverted`, calling a passing run unusable.

Fixed: stage parsing is now boot-aware (`stage_boot_count`, `stage_last_boot`, filtered
`stage_names`/`stage_uptime`), evaluation uses the **last** boot, and the verdict records
`stages.boots` and `stages.boot_id`. Two selftest cases cover the retried log and the case
where only an earlier boot reached multi-user. Selftest: 76 passed, 4 skipped (the skips are
the install guards, because both external disks are mounted right now).

## Defect 2 (documentation): the offline mask does not reach the booted /etc

`systemctl --root=/mnt/t2root mask bluefin-t2-hil-test.service` wrote
`/mnt/t2root/etc/systemd/system/bluefin-t2-hil-test.service -> /dev/null`, and
`systemctl --root` then reported `masked`. The booted system still ran the unit and powered
off during onboarding at 00:04:41. The booted `/etc` is the **deployment's** etc
(`/ostree/deploy/default/deploy/<csum>.0/etc`, per the sos report), not the top-level
`etc/` that an offline mount exposes. The mask landed in a directory the boot does not use.

Workaround (used for interactive sessions): boot with the kernel argument
`systemd.mask=bluefin-t2-hil-test.service` at the GRUB prompt. The runbook now says this.

## Defect 3 (fixed): `report` said not-ok after a successful firmware import

Wi-Fi worked, but `bluefin-t2 report` returned exit 1 (`verdict: not-ok`) and the observed
`firmware_state` was null: `harness/provision-firmware.sh` copies the payload into the
deployment's `/var/lib/firmware/brcm` but never wrote the import marker the report reads
(`/var/lib/bluefin-t2/firmware.state`). The marker is how the report distinguishes
“imported” from “absent”, and the copy route predates it.

Fixed: the script now writes `payload_sha256`, `source` and `files` after its own
verification step. `report` will say imported once the target is re-provisioned (or the
marker is written on the installed system).

## Defect 4 (observed, not fixed): first-login provisioning in the initial-setup session

The journal shows pkexec refusing the first-login helper while onboarding:

```
pkexec[1705]: gnome-initial-setup: The value for the SHELL variable was not found in the
/etc/shells file [USER=root] [COMMAND=/usr/libexec/bluefin-t2/provision-user]
```

The user unit runs in the **initial-setup greeter session**, so it tried to add
`gnome-initial-setup` to `kait2en-touchbar` and pkexec refused. The real user's first login
should trigger it once more from their own session; that path has not been observed yet.
If the group is still missing after a real login, this needs a design fix (a system-side
trigger, or a provisioning step that does not depend on pkexec from a greeter session).

## Defect 5: the first boot hit emergency mode — the target USB disk disconnected

The first boot after install did not reach userspace. The sos report records the sequence:

```
usb 2-4: USB disconnect, device number 5
I/O error, dev sdb, sector 2678432 op 0x0:(READ) ...
BTRFS critical (device sdb3): btrfs device id 1 has gone missing, can not maintain read-write
systemd[1]: Failed to start initrd-switch-root.service - Switch Root.
```

The external target disk dropped off the USB bus ~4.5 s into boot, btrfs aborted, and
switch-root failed. The retry boot worked. This is a USB enclosure/port reliability issue,
not an image bug, but it is a real Tier 2 risk: the target is a USB disk, and a disconnect
mid-initramfs cannot be recovered by the image. Retry first; if it recurs, change enclosure
or port and record it.

## Provenance note: the digest changed through `podman save`/`load`

The image built and gated locally was `e1f249ce…` (`sha256:e48422af…`); the digest the
install receipt and the booted system recorded is `sha256:a17cd966…`. Rootful podman cannot
see the user's image store, so the runbook transfers it with `podman save` + `sudo podman
load`, and the archive→storage round-trip recomputes the manifest digest. The attempt and
the result agree with each other, so the run is digest-pinned evidence about
`a17cd966…`; the chain back to the Tier 0 build is by image content, not by digest.

To close it, the next run should record the **image ID** as well (`podman image inspect
.Id`), which is preserved by the round-trip, in both the install receipt and attempt.json.
Until then, a bench digest must not be compared to a build digest.

## The interactive session (01:14–01:22, same run)

After the mask fix the machine stayed up and the operator ran
`harness/bench-interactive.sh` from the stick. Results:

| check | result |

| Fingerprint: `fprintd-enroll` | **FAIL: `NoSuchDevice: No devices available`** (fixed below) |
| Audio: five PipeWire sinks, speakers and headphones | **PASS** |
| Suspend/resume: keyboard, trackpad, Touch Bar, Wi-Fi | **PASS** |
| Hub: nine pages, launched from the app grid | **PASS** |
| `bluefin-t2 report` | not-ok before the firmware marker, **ok (exit 0)** after |
| Native audio DSP (`/usr/share/t2-dsp`) | **absent** (fixed below) |

Three product defects came out of this, all fixed in the same change:

1. **Provisioning never ran.** See the design's R2-9 correction: a user service is not a
   logind session, so the polkit action could not authorise. Replaced by
   `bluefin-t2-user-groups.service` + `.path` and a root helper; no pkexec anywhere.
2. **Touch ID had no bridge.** We shipped PAM + fprintd but not `t2-touchid`, which is the
   whole mechanism: the Secure Enclave keeps the fingerprint and the bridge feeds fprintd
   through libfprint's virtual device. `t2-touchid` is now packaged (binary, unit, fprintd
   drop-in, D-Bus policy, config), and `user-groups` sets `T2_TOUCHID_BIND_USER` to the
   first human account. Note the arming rule from KAIT2EN's documentation: the SEP keybag
   must be unlocked by a macOS login once since the T2 last *powered off* (reboots do not
   power-cycle the T2), and a finger must be enrolled under macOS.
3. **The audio DSP was not included.** `t2-dsp` is host-side PipeWire/WirePlumber graphs,
   FIR assets and udev model selection — no Apple firmware — so it is packaged into the
   image. Gate 18 asserts the profiles, udev rule, WirePlumber wiring and the LV2 plugins.

Two harness defects were fixed at the same time: `interactive-checks` treated
`fprintd-list`'s error output as a PASS, and treated a finished oneshot attach unit as a
FAIL. And the smoke test now powers off **only** when the run writes a `POWEROFF` marker
(`attempt.sh` does; `--interactive` does not), because on this hardware a power loss costs a
macOS boot before Touch ID works again.

## The second interactive session (03:05, new image)

The group provisioning worked on a fresh account (`groups: matt wheel kait2en-touchbar`).
Touch ID still failed, and the journal gave the exact reason:

```
kait2en-t2-touchid.service: Started
t2-touchid: watching /run/t2-touchid/fprint.sock for uid auto with flags 0x0
t2-touchid: cannot reach the sensor: interface enp230s0f1u1 has no IPv6 link-local address
```

`fprintd-list` found the bridge's virtual device (`Device at /net/reactivated/Fprint/Device/0`)
and reported "User matt has no fingers enrolled" — which the interactive check scored as a
PASS because it only matched the phrase "no prints". Two defects:

1. **The NCM profile did not autoconnect.** `nm-bridge` created "Apple T2 Bridge" with
   `connection.autoconnect no`; upstream's `t2-ncm.nmconnection` is `autoconnect=true`,
   `autoconnect-retries=0`. Without the link there is no IPv6 link-local, so the bridge (and
   `t2remote`, which logged the same wait) never reaches the T2. Fixed in the helper, which
   now reconciles an existing profile and brings it up; gate 11 asserts the semantics. A
   host-side `fix-t2-ncm.sh` repairs an already-installed disk.
2. **"no fingers enrolled" was scored as PASS.** The pattern now includes `no fingers`, and
   the check also fails when the bridge's journal says `cannot reach the sensor`.

**Audio DSP.** The package is in the image (profiles including `16_2`, udev rule,
WirePlumber config and LV2 plugins), but the session showed no `t2-*` ALSA card id and an
empty `wpctl` Filters section, so the graph did not activate on that boot. The interactive
checks now record both, and the journal from the next boot is the evidence needed to localise
it (udev rename vs WirePlumber component load).

## The scored run at 14:04 (run 20261021T215349Z-33e5) — fail on timing, and the real Touch ID delay

`result.json`: `fail / failed:modules`. The other four assertions passed, including the new one:

```
firmware: ok        wifi: ok        systemd_failed: ok        hygiene: ok
hygiene: blacklist_noise=0, btrfs_errors=0, bluetooth_devices=["hci0"],
         avc_denials=5, acpi_duplicates=18, tainted=12353
modules: missing=["hid_t2magicmouse"], unexpectedly_present=[]
```

**Why `hid_t2magicmouse` was missing.** The smoke test sampled at 14:04:19 (multi-user, 14 s in).
The internal trackpad is a USB Magic Trackpad that enumerates late; the kernel bound
`t2magicmouse` at **14:04:55**, 36 s after the snapshot. Upstream does not force this module in
the initramfs either (the host's `90-kait2en-input.conf` is the same six objects, and its
initramfs contains no copy), so this is a sampling bug in the gate, not a product fault.
Fixed: the module assertion now waits up to `MODULE_WAIT_S` (default 60 s) for the declared set
before failing, and records `waited_s`. The design's §5 list of five early objects including
`hid_t2magicmouse` is stale against the executable config on both trees; the six-object list is
the real one.

**Why Touch ID took ~20 minutes.** `nm-bridge` created the `Apple T2 Bridge` profile at
14:04:20 — after NetworkManager had already started and the device had appeared. The helper's
bounded `nmcli connection up` failed at 14:04:25 and NetworkManager did not auto-activate the
new profile; `kait2en-t2-touchid` started at 14:06:41 (it waits for `network-online.target`),
could not reach the sensor, and the link only reached `activated` at **14:24:35**, after a
resume re-evaluated the device. Fixed the way upstream does it: the profile now **ships as a
file** (`/etc/NetworkManager/system-connections/t2-ncm.nmconnection`, mode 0600,
`autoconnect=true`, IPv6 link-local), so NetworkManager sees it before it starts and the first
boot is as fast as every later one. `nm-bridge` only reconciles; it never activates the link.

The installed disk already has the runtime-created profile, so its *second* boot was fast —
which is why the delay looked like "the fingerprint scanner takes some time" rather than a
failure. A fresh install of the new image will not show it.

Rebuilt: bench `cbb7d1c0…` / `e1ed83de…`, release `3ac61195…` / `e571404f…`.
