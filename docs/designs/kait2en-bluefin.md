## Problem Statement

KAIT2EN-Fedora gives a T2 Mac a materially better Linux experience than anything else
available: suspend that works, a usable Touch Bar, working Touch ID, audio DSP, fan and power
control. Suspension is not folklore — this machine's journal records **30 `PM: suspend entry
(deep)` / `PM: suspend exit` pairs in 30 days**, including 04:26:00→04:38:01 and
04:53:04→05:01:48 today. It achieves this by keeping Fedora's stock kernel and adding 12 DKMS
source packages (18 `.ko`), one out-of-tree patched `amdgpu`, ~28 packages, and a large
userspace layer under `/usr/local`.

Bluefin Classic is the desired desktop, but it is immutable: `/usr` is a signed OCI artifact,
the kernel comes from `ghcr.io/ublue-os/akmods` and is versionlocked, and nothing may be
compiled on the host. KAIT2EN's entire delivery mechanism is host mutation — `dkms
build/install` into `/usr/lib/modules`, `grubby` on the live bootloader, `dracut --force` on
`/boot`, `systemctl enable` into `/etc`. None of it works there.

There is exactly one T2-on-atomic project today, `kansei-os/t2-atomic`. It solves packaging by
replacing Bluefin's kernel with a `sharpenedblade/t2linux` COPR kernel, deleting Bluefin's
akmods first. It has no Touch Bar support at all, does not install `t2-touchid` on the Bluefin
flavour, and **masks `suspend.target` twice**. So on the target hardware it has none of the
three things that make KAIT2EN worth using, and it is not a base to build on — it is a peer.

The gap is real, unbuilt by anyone, and its shape is: port a host-mutating hardware layer onto
an image-based OS while keeping the three behaviours that motivated it.

## What Makes This Cool

A T2 Mac becomes a first-class Bluefin machine: transactional updates, rollback when a kernel
breaks your keyboard, and sleep that works — the thing every other Linux-on-T2 user has given
up on and jokes about.

The second win is the install. Every existing atomic T2 image needs an external keyboard, an
external mouse and usually ethernet, because the installer environment has no T2 drivers.
KAIT2EN solved that without rebuilding the ISO: five input modules in a second initramfs on
the ESP plus a GRUB entry. That trick is the most under-appreciated asset in the project, and
it is what turns this from a variant into a product.

The third, quieter win: firmware handling that respects the licence boundary instead of
committing a 12 MB proprietary tarball to a public repo, while still being two clicks for the
user.

## Constraints

1. **`/usr` is read-only and image-owned.** Nothing compiles modules, installs packages or
   writes `/usr/share` at runtime.
2. **Kernel and modules are locked together.** Bluefin erases the base kernel, installs the one
   from `ghcr.io/ublue-os/akmods:<flavor>-<fedora>-<kver>`, and versionlocks it. A module built
   for any other release fails on vermagic. Concretely: Bluefin stable currently ships
   `7.2.5-200.fc44.x86_64`; this machine runs `7.2.11-200.fc44.x86_64`. Dev copies do not load
   on the other.
3. **Apple firmware is per-machine and non-redistributable.** Read from the running macOS at
   `/usr/share/firmware/wifi/{*.trx,*.clmb,*.txcb,P-*.txt}`; KAIT2EN explicitly refuses the
   redistribution packages. Verified: the four installed `brcmfmac4364b3-pcie.apple,trinidad-*`
   files are owned by no package, and Fedora's `linux-firmware` + `brcmfmac-firmware` contain
   zero Apple firmware files.
4. **The build host is not a T2 Mac.** Every DMI/PCI gate in KAIT2EN's installer silently takes
   the "not my model" branch in a container. Gates move to runtime or to "MacBookPro16,2 only".
5. **Secure Boot must not be silently unsolved.** An unloadable input module makes the machine
   unrecoverable by its owner.
6. **KAIT2EN is not an upstream target for drive-by AI patches.** Its `README.md` says it will
   reject PRs and issues when it notices AI involvement and asks to be talked to in person.
   This project consumes KAIT2EN; it does not open PRs against it.
7. **KAIT2EN's trademark policy binds the shipping name.** `TRADEMARK.md` grants factual
   reference ("based on, compatible with, derived from KAIT2EN") but requires permission to use
   the name for a fork, distribution, product or service. See Naming below.
8. **Image build cost** 30–60 min and 20 GB+ disk; 45–90 min for DX. Bounds iteration only.

## Premises

Confirmed with the author before writing:

1. KAIT2EN's code ports; its mechanism does not. DKMS becomes prebuilt signed kmods.
2. Bluefin has no T2 support to extend. `t2-atomic-bluefin` is a peer image, not a base.
3. The published image cannot contain Apple firmware.
4. Reuse ublue's akmods pattern for module delivery, not t2-atomic's kernel swap.
5. Secure Boot is a fork in the road, not a detail. **Resolved below: v1 signs and enrols.**
6. The image build does not belong on the Mac.

## Decisions taken after review

- **Shape of the image: a thin derivative, and the initramfs is regenerated in it.** Bluefin's
  `03`/`19` ordering does not apply to a `FROM` derivative; the derivative installs the kmods
  and then runs `dracut` itself. Stated in full under Artifact 2.
- **Signing is committed for v1**, with one key, and MOK enrolment happens from the live
  installer environment before the installed system's first boot. Secure Boot off is a
  documented degraded path, not the design.
- **v1 supports MacBookPro16,2 only.** Everything else is an explicit non-goal, so no DMI gate
  has to work at runtime in v1 except the Touch Bar's.
- **Bluefin DX is out of v1.** No requirement in this document mentions it, and it doubles the
  build and HIL matrix at the stage where the test loop is the scarcest resource.
- **Shipping name is neutral** (`bluefin-t2`), because `TRADEMARK.md` requires permission to use
  the KAIT2EN name for a distribution. Docs may say "includes KAIT2EN's T2 support". See
  Naming.

## Author's scope intent

Recorded 2026-10-20, after approval, for the review pipeline. These are inputs, not decisions —
the CEO review owns the scope call.

- The product is a **solid, usable workstation system for T2 MacBooks generally, especially the
  Intel models Apple no longer supports** — not a fix for one machine. v1's
  MacBookPro16,2-only scope is therefore a *sequencing* decision: it bounds what gets tested
  first, not who the product is for. How much multi-model work belongs in v1, and which models
  are worth supporting at all, is an open scope question.
- Bluefin **Dakota** and **Utah** are on the upstream roadmap. **Forwards compatibility with them
  is a desired bonus, not a requirement.** Classic is the target. No v1 decision may depend on
  Dakota or Utah timelines, and no v1 work should make a later port structurally impossible
  (the `akmods-t2` split and the `FROM`-derivative shape both survive a base-image change, which
  is the cheapest forward compatibility available).

## Approaches Considered

**A: fork `akmods` → `akmods-t2`, thin Bluefin derivative.** Kernel and modules produced
together, signing reuses the proven path, T2 arrives the way nvidia/zfs already do. Effort XL,
completeness 10/10. **Chosen.**

**B: one repo, modules built in our own CI.** Compile per build against the base image's
kernel, sign with a CI secret, install the RPMs. Effort L, completeness 7/10. Reimplements the
lockstep akmods enforces, with no versionlock discipline. **Kept as the descope fallback** — it
is the same `06-t2-modules.sh` contract with a local build instead of an OCI cache.

**C: installer-first.** Port the macOS kit so a T2 Mac installs with no external hardware.
Effort M–L, completeness 6/10 standalone. **Chosen jointly with A**, because the install is the
product and the firmware capture is mandatory for every approach.

**Rejected: sysext-only, no image.** A systemd-sysext merged at runtime is not in the
initramfs, so the input modules would be unavailable before root is mounted — no LUKS
passphrase, no recovery shell. Sysext stays a candidate home for *apps and firmware* in v2, not
for modules.

## Recommended Approach

**A + C: two repos, three artifacts, one HIL rig.**

- **Repo 1 — `akmods-t2`**: a fork of `ublue-os/akmods` that builds 12 kmod RPMs for the exact
  kernel Bluefin publishes, signs them, and publishes an OCI cache.
- **Repo 2 — `bluefin-t2`**: the image (`FROM ghcr.io/ublue-os/bluefin`), plus `installer/` — the
  retargeted macOS kit, released as an asset from the same repo.

### Artifact 1 — `akmods-t2`

- Resolve the target kernel from the published image, not from akmods:
  `skopeo inspect docker://ghcr.io/ublue-os/bluefin:stable | jq -r '.Labels["ostree.linux"]'`.
  Bluefin sets that label at publish time (`Justfile:219`) and resolves its own kernel the same
  way (`Justfile:153`). Current value: `7.2.5-200.fc44.x86_64`.
- **The packaging work does not exist yet and is the bulk of the estimate.** KAIT2EN has no
  `akmod-*` spec, no `kmodtool`, no akmods anywhere — every module has only a `dkms.conf`. So:
  12 specs, one per DKMS package name (`t2bce_stack`, `t2smc`, `t2bdrm`, `t2touchbar`,
  `hid_t2magicmouse`, `t2_precision_trackpad`, `t2_trackpad_actuator`, `t2mfi_fastcharge`,
  `t2gmux`, `t2thunderbolt`, `t2smp`, `t2sbs`), built with `akmods --force --kernels <kver>`;
  `t2bce_stack` alone produces five objects (`t2bce_dma`, `t2bce_core`, `t2bce_vhci`,
  `t2bce_audio`, `t2bce_ave`) in one RPM. Each spec carries KAIT2EN's `dkms.conf` version so
  review stays per-module. Per-kernel compat patches mirror KAIT2EN's own practice
  (`patches/fedora-44-input.patch`); a compile failure on a kernel bump fails CI by
  construction, which is the point.
- **The 18 objects, enumerated**, so nothing downstream asserts a bare count. Verified on the
  target by `modinfo -n` resolving every one of these names to a `.ko.xz`:

  | Spec | Objects |
  |---|---|
  | `t2bce_stack` | `t2bce_dma`, `t2bce_core`, `t2bce_vhci`, `t2bce_audio`, `t2bce_ave` |
  | `t2touchbar` | `t2hid`, `t2touchbar_bl`, `t2touchbar_kbd` |
  | `t2smc` `t2bdrm` `hid_t2magicmouse` `t2_precision_trackpad` `t2_trackpad_actuator` `t2mfi_fastcharge` `t2gmux` `t2thunderbolt` `t2smp` `t2sbs` | one each |

  That is 5 + 3 + 10 = 18 across 12 specs. Note for the earlier review record: a round-2
  finding claimed this sums to 16 by counting the ten single-object specs as eleven; the
  enumeration above is verified against the machine, and `dkms status` reports exactly 12
  packages. On a MacBookPro16,2 `t2gmux` is expected to load and stay unbound — there is no GPU
  mux device on this model — so the Tier 0 and Tier 2 assertions are a **named set with expected
  absentees**, not "18 things must be bound".
- **Signing: one key, one signature.** We reuse Bluefin's kernel, which is already Fedora- and
  ublue-signed, and we do not hold the kernel-signing key — so there is no reason to dual-sign.
  The real sequence, taken from `dual-sign.sh:15-22` and reduced to one signer: build a
  `signing_key.pem` (private key + cert concatenated), `openssl cms -sign -signer signing_key.pem
  -binary -in <mod> -outform DER -out <mod>.cms -nocerts -noattr -nosmimecap`, then
  `/usr/src/kernels/<kver>/scripts/sign-file -s <mod>.cms sha256 public_key_chain.pem <mod>`,
  then verify each module immediately by extracting the signature and running
  `openssl cms -verify -certfile public_key_chain.pem -noverify`.
- Publish `ghcr.io/<org>/akmods-t2:<flavor>-<fedora>-<kver>`, cosign-signed. Ship the DER at
  `/etc/pki/akmods/certs/` following the `ublue-os-akmods-addons` convention.
- Triggers: daily cron chasing the Bluefin image's kernel label; `repository_dispatch` on
  KAIT2EN movement; manual.

### Artifact 2 — `bluefin-t2` (the image)

One `Containerfile`, `FROM ghcr.io/ublue-os/bluefin:<fedora>@<digest>`. Because the upstream
`03`/`19` build steps have already run and the initramfs is already baked, the derivative owns
five things, in this order:

1. **`06-t2-modules.sh`** — `skopeo copy` the `akmods-t2` image matching the kernel now present
   in the build, unpack, `dnf5 -y install` the kmod RPMs, `depmod -a -v "$KERNEL"`, write
   `/usr/lib/modules-load.d/t2-*.conf` for anything that must autoload.
2. **`07-t2-packages.sh`** — runtime and build packages, split honestly.
   *Runtime:* `fprintd`, `fprintd-pam`, `libfprint`, `polkit`, `alsa-ucm`,
   `pipewire-module-filter-chain-lv2`, `lv2-bankstown`, `lsp-plugins-lv2`, `lm_sensors`,
   `authselect`, `plymouth-plugin-script`, `adwaita-sans-fonts`.
   *Build-only, erased before commit:* `cargo`, `rust`, `gtk4-devel`, `libadwaita-devel`,
   `libinput-devel`, `libplist-devel`, `systemd-devel`, `glib2-devel`, `rpm-build`,
   `pkgconf-pkg-config`, `gcc`, `make`, `checkpolicy`, `policycoreutils`, `selinux-policy-devel`.
   `gcc`, `make`, `checkpolicy` and `policycoreutils` are build-only because nothing at runtime
   compiles — `t2-kernel-builder` is excluded. KAIT2EN's full list is
   `install-dependencies.sh:24-62`; the split is ours, and Tier 0 asserts the build-only set is
   absent from the committed image.
3. **`08-t2-apps.sh`** — build the 8 shipped desktop apps from the pinned KAIT2EN submodule as
   RPMs (not `/usr/local`, which on ostree is a symlink to `/var/usrlocal` and therefore not
   image content): `t2-fan-control`, `t2-smc-control`, `t2-power-explorer`, `t2-zone-power`,
   `t2-journal`, `kait2en-touchbar`, `t2-power-tune`, `t2-force-click`, plus the `t2remote`
   helper. Cache generation runs here: `fc-cache -f`, `gtk-update-icon-cache`, `dconf update`.
   **Not shipped in v1:** `t2-kernel-builder` (its purpose is building kernels on the host),
   `t2-hybrid-gpu-control` and `t2-dgpu-control` (their model gates exclude MacBookPro16,2).
4. **`09-t2-policy.sh`** — the two policy changes that cannot be made at runtime:
   - **SELinux.** Compile KAIT2EN's `t2-touchid` policy from
     `t2-touchid/integration/selinux/` with `checkmodule` + `semodule_package` (the sequence in
     that directory's `Makefile:6-9`), install it with `semodule -X 400 -i`, and ship the sources
     under `usr/share/selinux/kait2en/`. Without this step Touch ID's policy does not exist and
     Tier 0's positive assertion has nothing to assert. Only `restorecon /run/t2-touchid` remains
     a runtime action.
   - **PAM.** `authselect select $(authselect current --raw 2>/dev/null | head -1) with-fingerprint`
     at build time. This is the step whose absence would have left enrolment working and login
     never offering the fingerprint. KAIT2EN does it at runtime with receipt/rollback logic
     (`lifecycle.py:395-403`); on an image the build owns it and the rollback logic is dropped.
5. **`10-initramfs.sh`** — `dracut --force --no-hostonly --kver "$KERNEL" --reproducible --add
   ostree`, exactly as Bluefin's own `19-initramfs.sh` does, so the T2 modules and our dracut
   drop-in land in the image initramfs. **This is the step the earlier draft left unassigned.**
   The build then ends with `bootc container lint` and our own `90-tests.sh`; Bluefin's
   `20-tests.sh` is not ours and does not run against a derivative, so our gates replace it.

**Touch ID needs more than a unit.** Complete file set: the fprintd drop-in
`etc/systemd/system/fprintd.service.d/`, the D-Bus system policy under `usr/share/dbus-1/system.d/`,
`etc/kait2en/t2-touchid.conf`, the SELinux policy from step 09, and `fprintd-pam` plus the

never offers the fingerprint. The per-user binding that `install-touchid.sh:28-30` writes at

`kait2en-touchid-bind.service`: a **user** unit that runs once per user (marker

system service on its own, so the helper and its action are shipped, not assumed. The fingerprint
path also rides the internal CDC-NCM link, so the NetworkManager `Apple T2 Bridge` profile and
`etc/NetworkManager/conf.d/10-t2-services.conf` (`no-auto-default=ac:de:48:00:11:22`) are v1
content; the profile binds by MAC, so `kait2en-nm-bridge.service` creates it on first boot rather
than baking it.

**Not ported, with reasons:**

- Patched `amdgpu` and the hybrid/dGPU apps — model gates exclude MacBookPro16,2.
- `t2-kernel-builder`, `kait2en-multicall`'s `grub2-mkconfig`, `kait2en-install` /
  `kait2en-prepare`, all migration/cleanup code — each contradicts the image model.
- The `gnome-shell-theme.gresource` replacement — open question, not a fait accompli.
- ACPI overrides — require this machine's firmware tables and kernel log. **v1 ships nothing.**
  v2 route: first-boot generator writing to `/etc/kait2en/acpi`, then `rpm-ostree initramfs-etc
  --track` + `rpm-ostree initramfs --enable`. Unverified on Bluefin 44.

**DMI gates, made explicit.** v1 ships the 11 base kargs with no model exceptions and supports
MacBookPro16,2 only. The one gate that must work at runtime in v1 is the Touch Bar, and it uses
`ConditionPathExists` on the t2bdrm DRM node, so the units no-op on a model without a bar rather
than failing at every boot. Everything else is a stated v2 item, not an untracked assumption.

**Two initramfs module sets, deliberately different, both asserted by name:**

- *Installed image* (`90-t2-input.conf`, copied verbatim from the live host's
  `/etc/dracut.conf.d/90-kait2en-input.conf`): `t2bce_dma t2bce_core t2bce_vhci t2hid t2smc
  t2sbs` — six modules. The BCE stack plus HID quirks give a keyboard and trackpad before root;
  `t2smc` and `t2sbs` are there because KAIT2EN put them there, and our gate asserts KAIT2EN's
  list rather than inventing one.
- *Live installer* (the kit's `build-input-kmod.sh:55`): `t2bce_dma t2bce_core t2bce_vhci
  t2touchbar hid_t2magicmouse` — five modules, built into `kait2en-input-0.1` by
  `kmod-kait2en-input.spec`. It carries the trackpad driver instead of the battery/thermal pair
  because the live environment does not need those.

### Artifact 3 — the macOS kit, in `bluefin-t2/installer/`

Fork of `scripts/macos/` plus `auto-installer/`, retargeted from Fedora editions to our ISO.

- Keep verbatim: ISO download and verify, external-disk write, ESP edit, `grub.cfg.in` rewrite,
  `build-input-kmod.sh` (already parameterised by source root, kernel release and output dir),
  `collect_macos_firmware` / `collect_macos_bluetooth_firmware`
  (`prepare-fedora-installer.sh:152-213`), and the cpio-to-ESP carry.
- Retarget: `targets/fedora-44.conf` → our ISO; `fedora-44-editions.tsv` → `bluefin`.
- **Drop the Anaconda addon entirely.** Its real jobs are firmware installation into the target
  sysroot, the transition kmod RPM, and kernel args. All three are satisfied by the image or by
  first boot: the transition modules are in the image's initramfs, kargs are in `kargs.d`, and
  firmware is imported on first boot. Live-input injection was never an addon job — it is the kit
  writing `kait2en-input-initramfs.img` plus a GRUB entry onto the ESP, and it stays exactly that.

**Two install routes, not three.** The earlier draft's "install, then `bootc switch` from the live
env" was wrong: `bootc switch` operates on the system it runs in, not on another disk's
installation, so it would have changed nothing and the installed stock Bluefin would have booted
with no input.

| Route | Mechanism | External hardware |
|---|---|---|
| 1. Kit-prepped `bluefin-t2` ISO (BIB) | install runs the image; firmware pre-seeded on the ESP | **none** |
| 2. Already on Bluefin | `sudo bootc switch ghcr.io/<org>/bluefin-t2:stable && sudo reboot` | one reboot on an external keyboard |

Route 2's keyboard is unavoidable because the running stock Bluefin has no T2 input modules; the
rebase fixes that permanently after the reboot. This is why route 1 is the headline route and
why success criterion 1 is scoped to it.

### Firmware channel — concrete

- Carrier: `/boot/efi/kait2en/firmware/` on the installed ESP, written by the kit. The installed
  system mounts it at `/boot/efi` on every boot; no extra mount is needed.
- Destination: `/var/lib/firmware/brcm/`, selected by `firmware_class.path=/var/lib/firmware`
  in `kargs.d`. Verified on target: `/sys/module/firmware_class/parameters/path` exists and the
  parameter is real.
- Trigger A (pre-seeded payload): `kait2en-firmware-import.service` oneshot,
  `ConditionPathExists=/boot/efi/kait2en/firmware/wifi`.
- **Reloading the driver, done correctly.** `brcmfmac` probes when the PCI device appears, before
  the payload exists in `/var`. Proving `/var` is mounted does not prove the file is there. And
  the driver cannot simply be removed afterwards: at that point the PCI function is **bound**, so
  `modprobe -r brcmfmac` fails with `module in use`. The sequence the unit must run is
  **unbind, install, rebind**:
  1. `echo 0000:e5:00.0 > /sys/bus/pci/drivers/brcmfmac/unbind` (the bus id is discovered, not
     hard-coded — `14e4` with any of the T2 device ids),
  2. `modprobe -r brcmfmac_wcc; modprobe -r brcmfmac`,
  3. run KAIT2EN's `install-wifi-firmware.sh` against `/var/lib/firmware`,
  4. `modprobe brcmfmac`, then `echo 0000:e5:00.0 > /sys/bus/pci/drivers/brcmfmac/bind` (or a
     PCI remove/rescan pair if the bind path is unavailable).
  Step 1 is what the earlier draft got wrong: without it the reload cannot happen and first-boot
  Wi-Fi depends on NetworkManager happening to retry.
- **Ordering.** The unit runs `After=systemd-udev-settle.service` and **`Before=network-online.target`,
  NetworkManager.service**, declares `Wants=network-pre.target` and `Before=network-pre.target`,
  and restarts NetworkManager at the end (`systemctl restart NetworkManager`) so association does
  not depend on an unspecified retry. Ordering is asserted in Tier 0 by parsing the unit, and the
  resulting association is asserted in Tier 2.
- The name derivation is not a guess: the unit reads the failed-load lines the first probe left in
  the kernel log, which is exactly what KAIT2EN's `install-wifi-firmware.sh:96-145` needs to derive
  `brcmfmac<chip>-pcie.apple,<board>-...` names.
- Trigger B (payload arrives later, USB or route 2): `kait2en-firmware-import.path` watching the
  ESP directory, plus a manual `kait2en-import-firmware <dir>` command. A boot-time oneshot
  cannot fire on a USB inserted afterwards, which is why the path unit exists.
- When the payload is absent: no Wi-Fi, a desktop notification from the import unit, and
  `kait2en-firmware-status` reporting `absent` and where to put the files. Nothing else degrades.

### Test strategy — four tiers

**Tier 0 — container conformance, no T2 hardware, no reboot.** Runs in CI on every commit, in a
dedicated harness image `ghcr.io/<org>/t2-test-harness` that carries `kernel-devel` for the
target release, `dracut`, `systemd`, `openssl`, `kmod` and `python3`. Assertions run in the
harness against the built image's filesystem mounted read-only — **not** inside the image, which
has had `/usr/src` and `kernel-devel` removed by Bluefin's `05-override-install.sh` and therefore
cannot run `scripts/extract-module-sig.pl`. Asserts:
- every `.ko` in the named 18-object set present for the target kernel; `modinfo -F vermagic`
  equals `<kver>`; `depmod -a` reports no unknown symbols; `modprobe --dry-run` proves dependency
  order and existence only. Symbol *resolution* is proven by `depmod`'s clean run plus the actual
  load in Tier 2 — there is no VM tier, and the earlier draft's reference to one was wrong.
- signature verifies per module via `extract-module-sig.pl` + `openssl cms -verify -certfile`.
- initramfs built for the target kernel, then `lsinitrd` asserts **both** named module lists.
- `systemd-analyze verify` on all 15 units (plus the 3 harness-only units in the harness image);
  `systemctl --root=<image> preset-all --dry-run` then assert the generated `*.wants` symlinks
  exist.
- the SELinux policy module is present at priority 400 and `semanage module -l` lists it.
- `/etc/pam.d/system-auth` and `password-auth` contain `pam_fprintd.so` after the
  `authselect ... with-fingerprint` step; the build-only package set (`gcc`, `make`,
  `checkpolicy`, `policycoreutils`, `rpm-build`, `cargo`, `rust` and the `-devel` packages) is
  absent from the committed image.
- `udevadm verify`, `pkaction --verbose`, `desktop-file-validate`, `appstreamcli validate`,
  PipeWire/WirePlumber config parse, `alsaucm` profile load.
- `bootc container lint`; policy assertions phrased as **"no runtime unit, script or image-owned
  hook invokes `grubby`, `dkms` or `semodule`; no `/boot` writes; nothing under
  `/etc/kernel/install.d`"** — the image build does run `semodule -i` by design, so the SELinux
  module's presence is a separate positive assertion.
- kargs TOML parsed and compared to the expected 12-argument list.

**Tier 1 — live host, real hardware, no reboot.** The host is a T2 Mac; most CI cannot offer
that.
- Compile the modules against `$(uname -r)` = `7.2.11-200.fc44.x86_64` and load **only modules
  that do not carry the active input path** — `t2smc`, `t2thunderbolt`, `t2mfi_fastcharge`,
  `t2smp`. Never `t2hid`, `t2bce_*` or `hid_t2magicmouse`: unloading those locks out the keyboard
  on the machine doing the test, which Constraint 5 calls unrecoverable.
- Preconditions: an external keyboard attached or a second boot target available, and the
  rollback command stated per step (`modprobe <dkms-built module>` from
  `/usr/lib/modules/$(uname -r)/updates/dkms/`).
- Validate the packaged userspace against live hardware: `t2smc` hwmon sensors, audio profile
  selection, `fprintd-list`.

**Tier 2 — hardware-in-the-loop, image under test.**
- Install invocation, pinned and recorded:
  `sudo podman run --privileged --pid=host --rm -it -v /dev:/dev -v /var/lib/containers:/var/lib/containers
  quay.io/fedora/fedora-bootc:44 bootc install to-disk --source-imgref
  ghcr.io/<org>/bluefin-t2@sha256:<digest> /dev/nvme1n1`. `bootc` is absent from the host
  (verified), so it comes from the container. The tested digest is written into the results JSON
  so every HIL run is tied to an artifact.
- **The results partition lives on a separate device, not on the disk being installed to.**
  `bootc install to-disk` claims the whole target device and repartitions it, so a results
  partition cannot coexist with it, and the internal root is LUKS-encrypted so results cannot go
  there either — the earlier draft contradicted itself on this. Results go to a dedicated small
  FAT32 USB stick (`K2B-HIL`), mounted at `/run/media/<user>/K2B-HIL` on the host and at
  `/var/mnt/hil` on the test system via a unit in the harness image. If someone wants a single
  disk, the supported alternative is partition-by-hand plus `bootc install to-filesystem`, which
  is stated here only as an option, not as the default.
- **Failed-boot capture, done at the right layer.** A `sysinit.target` marker cannot observe the
  failures that matter — a missing initramfs module, a panicking module or bad kargs fail before
  it. So the attempt marker is written **before boot, by the host-side harness**, into the
  `K2B-HIL` stick: `attempt.json` with the tested digest and a timestamp. Three outcomes:
  1. `attempt.json` + `result.json` → pass or fail, recorded by `kait2en-hil-test.service`.
  2. `attempt.json` with no `result.json` after the harness's timeout → `FAILED_BOOT`, written to
     the stick by the host on the next run, with the digest, the timeout and the operator's screen
     photograph path.
  3. No `attempt.json` at all → the harness never started; recorded as `HARNESS_ERROR`.
  A T2 Mac has no serial console, so the photograph is the capture path for case 2 and it is
  referenced from the record rather than left implicit.
- The payload is pre-placed on the external disk's ESP *after* `bootc install to-disk` and
  before first boot, so the first-boot import path is exercised for real.
- The smoke test asserts the **named 18-module set** (enumerated in Artifact 1), not a count, and
  records which of them are expected absent on this model (`t2gmux` has no GPU mux device on a
  MacBookPro16,2, so it is expected to load but stay unbound). Plus: no `firmware load failed` in
  `dmesg`, Wi-Fi associated, Touch Bar present and usable **as the desktop user** (R2-16),
  `fprintd-list` non-empty, fingerprint offered at the lock screen, `systemctl --failed` empty,
  **one suspend/resume cycle**, `wpctl status` shows the DSP sink. Then power off.
- Recovery contract: never install to the internal disk; Option-boot back; previous deployment
  pinned.

**Tier 3 — kit and ISO, gated.** One HIL run per ISO build using the real kit and a real USB:
the ESP initramfs injection, the GRUB rewrite, the firmware capture and carry, and a clean
install with no external hardware attached. Its result goes to the results partition like
Tier 2. Without this, the headline success criterion rests on untested code.

Rough cadence: Tier 0 every push, Tier 1 before a HIL run, Tier 2 per image change, Tier 3 per
ISO build — 15–20 minutes per HIL cycle.

### Naming, licensing and supply chain

- **Name.** `TRADEMARK.md` requires permission to use "KAIT2EN" for a distribution. Ship as
  `bluefin-t2`; docs say "includes KAIT2EN's T2 support". Open a conversation with the
  maintainers — which is also what their `README.md` asks for — before any name that uses theirs.
- **Licences.** Image userspace is mostly GPL-3.0-or-later, kernel modules GPL-2.0. Publishing
  the image is distribution, so each release publishes a corresponding-source tarball
  (KAIT2EN submodule at the pinned commit plus our patches) and a `source-<version>` tag, and
  the kit ships under GPL-3.0-or-later with a `NOTICE` naming the fork point.
- **Registry policy.** `bootc switch --enforce-container-sigpolicy` reads
  `/etc/containers/policy.json`, which arrives from `projectbluefin/common` and pins ublue's
  keys. The build appends our registry and cosign key to that file; without it the verification
  claim would be false for users.
- **Kit distribution.** No `curl | bash` for a tool that rewrites an ESP. Publish the kit as a
  release asset with a SHA-256 and a cosign signature; the documented command downloads,
  verifies, prints the target disk and requires a typed confirmation.

### Distribution

- `ghcr.io/<org>/bluefin-t2:{stable,latest}` and `ghcr.io/<org>/akmods-t2`. Cosign-signed with
  our key, public key in the repo. No DX in v1.
- ISO as a GitHub release asset with checksums, built by BIB.
- Rebuild: daily cron against Bluefin Classic; dispatch on KAIT2EN main; manual. A stale image
  is worse than none because the kernel moves underneath it.

## Open Questions

1. **Key custody.** One signing key in CI secrets, generated offline, with a documented
   rotation. Needed before Artifact 1 is publishable; the design assumes CI-held, not on-disk.
2. **`rpm-ostree initramfs-etc --track`** on Bluefin 44 — the only plausible route for
   per-machine ACPI overrides in v2. Needs a one-line probe before v2 relies on it.
3. **GNOME shell `gresource`.** Rebuild in the image, or drop the black lock screen. It
   overwrites a gnome-shell-owned file.
4. **Multi-model coverage.** Everything is validated on one MacBookPro16,2. BCM4377 Bluetooth,
   the AMD GPU models, the `hci_bcm4377` board-table gap, and the non-Touch-Bar units are all
   untested and explicitly out of v1.
5. **KAIT2EN upstream drift.** Consumed as a pinned submodule with no coordination and no PR
   channel. Divergence is managed by rebasing.
6. **Compile compatibility.** Nothing yet proves the 18 modules compile unmodified against

   practice exists for a reason; a compile failure is a scheduled risk, not a surprise.

## Success Criteria

- On a MacBookPro16,2, **route 1** (kit-prepped ISO) installs with no external keyboard, mouse
  or ethernet. Route 2 is exempt and says so.
- The **named 18-object set** from Artifact 1 loads, asserted in **both** Secure Boot states:
  (a) SB off — expected to load; (b) SB on with our DER enrolled — expected to load, and the
  keyboard works in the initramfs; (c) SB on, not enrolled — expected to fail. (c) is not
  reachable on the designed route, because enrolment happens before the installed system's first
  boot; to test it, deliberately skip enrolment on a throwaway install, and the recovery is
  re-running the kit or the live medium with an external keyboard, not "boot the previous
  deployment" (a fresh install has none). Secure Boot is switched in the Mac's startup security
  utility between runs, and each state is recorded with the tested digest. Criterion passes only
  when (a) and (b) both hold.
- Wi-Fi associates on first boot after the payload is imported, with no manual step beyond
  running the kit; and the import unit's driver reload is proven by Tier 2.
- Suspend and resume work for ten consecutive cycles. The baseline exists: 30 clean cycles in 30
  days on this machine.
- Touch Bar renders the KAIT2EN bar; Touch ID authenticates through fprintd; internal speakers
  use the 16_2 DSP profile; fans follow the KAIT2EN curve.
- `bootc upgrade` to a new Bluefin kernel either works or fails Tier 0 in CI — never ships a
  mismatched vermagic.
- Rollback from the boot menu restores a working machine after any failed update.
- Tier 0 green on every commit; one Tier 2 run per image change and one Tier 3 run per ISO build,
  recorded in the results partition with the tested digest.

## The Assignment

Prove the module pipeline on its own, with no image involved, and accept that it needs **two
kernel builds, not one**.

First: build `t2smc` from the KAIT2EN sources for **your host's kernel**
(`uname -r` = `7.2.11-200.fc44.x86_64`), sign it with your new key, unload the DKMS copy with
`modprobe -r t2smc`, load yours with `modprobe t2smc`, and confirm it binds — `sensors` shows the
fan and temperature channels, `modinfo t2smc` reports your signature. That proves the sources and
the signing path against a real T2 kernel. It does **not** require touching the keyboard modules,
and the rollback is `modprobe t2smc` from `/usr/lib/modules/$(uname -r)/updates/dkms/`.

Second: build the same module for **Bluefin's kernel** (`7.2.5-200.fc44.x86_64`, read from the
image's `ostree.linux` label) and verify it *without loading it* — `modinfo -F vermagic` matches,
`depmod` reports no unknown symbols, and the CMS signature verifies against your DER. It cannot
load on your host, and that is the point: the two kernel releases differ, which is exactly the
lockstep the whole design exists to respect.

If both pass, the rest of this design is packaging. If either fails, you have found the actual
hard part in a day rather than in week six.

> The first-login bind unit's mechanism is unspecified where it matters. `kait2en-touchid-bind.service` is described as `a first-login user unit that writes T2_TOUCHID_BIND_USER for the logged-in user and restarts the service`, but a systemd user unit cannot restart a system service without a shipped polkit action or a root helper, and `first login` needs a per-user marker or preset rule that is never stated. Installed as described, the Touch ID binding would not be applied.

**Remedy**

> Choose and state the mechanism (polkit-authorized helper called by the user unit, a PAMName=/pam_exec hook, or a documented one-time root command), ship the polkit action, state how first login is detected, and add the unit to the inventory and Tier 0.

### R2-10 — feasibility

**Problem**

> The brcmfmac reload cannot work as written and its ordering is still unstated. Trigger A runs `modprobe -r brcmfmac_wcc brcmfmac` after the coldplug attempt, but the PCI device is bound to `brcmfmac` at that point, so removal fails with `module in use` unless the device is unbound (or removed and rescanned) first. The carried obligation from round 1 also remains unmet: the unit is not ordered relative to NetworkManager and `network-online.target`, so first-boot association depends on an unspecified NetworkManager retry.

**Remedy**

> Unbind the PCI device (or remove/rescan it) before removing the module, reload after the payload is in `/var/lib/firmware/brcm`, order the unit after the coldplug attempt and before `network-online.target` (or restart NetworkManager after the reload), and assert first-boot association in Tier 2.

### R2-11 — feasibility

**Problem**

> The failed-boot capture still cannot observe the failure class that motivated it. `kait2en-hil-early.service` is bound to `sysinit.target`, so a boot that fails in the initramfs or kernel - the document's own examples (missing input module, panicking module, bad kargs) - writes neither `boot-attempt` nor a JSON; the stated rule only covers `If boot-attempt exists without a JSON`, and has no branch for the no-marker case, so the honest capture remains an operator photograph that the harness never records as an outcome.

**Remedy**

> Put the attempt marker before the failure point (the harness writes it to the results partition before boot, or the initramfs writes it), define the timeout/no-marker branch that records `FAILED_BOOT` with the tested digest and the screen photograph, and say where that record is written.

### R2-12 — feasibility

**Problem**

> The HIL results partition has no home under the stated install invocation. Tier 2 installs with `bootc install to-disk ... /dev/nvme1n1` (whole target device, no partition layout) and at the same time says `the external disk carries a results partition both systems can mount`, while the internal root is LUKS-encrypted `so results cannot go there`. `bootc install to-disk` repartitions its target, so the results partition's location, creation and survival across the install are undefined.

**Remedy**

> State where the results partition lives (a second disk/USB, or a supported partitioned install such as `to-filesystem`), how it is created and mounted by both systems, and update the install invocation so the two claims agree.

### R2-13 — feasibility

**Problem**

> The two pipelines' kernel lockstep is asserted but not specified. Artifact 2 says `skopeo copy the akmods-t2 image matching the kernel now present in the build` without saying how the build determines that kernel, and the image base is pinned by digest while `akmods-t2` is tagged by kver. With independent triggers (Artifact 1 `daily cron chasing the Bluefin image's kernel label`, Distribution `daily cron against Bluefin Classic`), an image build can run before the matching module cache exists; the only stated fail-safe, `a compile failure on a kernel bump fails CI by construction`, addresses the module pipeline rather than this race.

**Remedy**

> State the kernel resolution (the base image's `ostree.linux` label or the `/usr/lib/modules` entry), make the image build fail closed with an explicit error when no `akmods-t2` tag matches, and define the trigger order so the akmods-t2 build/dispatch precedes the bluefin-t2 rebuild.

### R2-14 — completeness

**Problem**

> The runtime/build package split is incomplete and partly inverted. Step 07's build list lacks tools the committed steps need: `rpm-build` (step 08 builds the apps `as RPMs`), `pkgconf-pkg-config` (Rust/GTK builds), `adwaita-sans-fonts` (the Touch Bar app's font, evidence base `apps/t2-touchbar/install.sh:57`) and `plymouth-plugin-script` (the shipped Plymouth theme's script plugin); the runtime list contains `checkpolicy`, `policycoreutils`, `gcc` and `make`, which are needed only at build time (nothing at runtime compiles, since `t2-kernel-builder` is excluded), and `fprintd-pam` is missing (see R2-4).

**Remedy**

> Complete both lists from the design's evidence base (`install-dependencies.sh:24-62`, `install-dsp.sh:33-35`, `apps/t2-touchbar/install.sh:57`, `dsp/Makefile`), move `checkpolicy`/`policycoreutils`/`gcc`/`make` to build-only, and assert in Tier 0 that the build-only set is absent from the committed image.

### R2-15 — completeness

**Problem**

> The table said to carry `everything KAIT2EN writes into image-owned paths` omits the fonts, licence and wordmark. The JetBrains Mono fonts plus the OFL licence (`lib.sh:142-161`) and `kait2en-wordmark.png` (`install-apps.sh:143-147`) currently go to `/usr/local/share`, and no row moves them to a `/usr/share` path or names their owner; step 08's `fc-cache -f` therefore has no shipped font to index.

**Remedy**

> Add rows for `/usr/share/fonts/kait2en/*` with `/usr/share/licenses/kait2en-fonts/OFL.txt` and the wordmark asset, and state the `/usr/local` to `/usr/share` move for every shipped data file.

### R2-16 — completeness

**Problem**

> The Touch Bar app's per-user group membership is unassigned. The image ships the `kait2en-touchbar` sysusers entry and a udev rule that depends on that group, but KAIT2EN's `usermod -aG kait2en-touchbar` for the invoking desktop user (`apps/t2-touchbar/install.sh:63-64`) cannot run at build time, and the only per-user step the design defines is the Touch ID bind unit. On an image whose first user is created at first boot, the bar can ship and still be inaccessible to that user.

**Remedy**

> Add a first-login mechanism that adds the logged-in user to the group (or replace the group rule with a udev uaccess/TAG+= rule that needs no membership), state how the account is detected, and cover the Touch Bar as the desktop user in the Tier 2 smoke test.
