## Verdict

This is an unusually strong *packaging* plan and an under-scoped *product* plan. The A+C shape is
right, the evidence is cited to the line, the four-tier test strategy is better than most shipping
hardware projects, and the plan already knows the three things that kill T2-on-atomic projects
(sleep, Touch Bar, Touch ID over the NCM link). What it gets wrong is who it is for: it is written
as a validated build for one MacBookPro16,2, and its only proof-of-working tier requires that exact
machine on a bench — so "a workstation for T2 MacBooks generally", which is the stated product,
is unreachable **by construction** no matter how model-generic the code underneath already is.
Decision: keep the architecture, widen the *claim* to the class the code already serves, and spend
the one structural expansion available on making validation something a stranger can produce.

## The scope decision

**Recommendation: v1 supports a device *class*, not a model — and the class is the four 13-inch,
integrated-GPU, Touch Bar T2 MacBook Pros. The labelling stays two-tier: one model validated on
hardware, four models claimed by shared-code argument, with the argument written down.**

The set:

| Tier | Models | Basis |
|---|---|---|
| **Validated in v1** (Tier 2 HIL, success criterion) | `MacBookPro16,2` | The bench machine. `docs/designs/kait2en-bluefin.md:13-17` |
| **Supported in v1, same device class** | `MacBookPro15,2`, `MacBookPro15,4`, `MacBookPro16,3` | See the four-part argument below |
| Deferred (class B, dGPU) | `MacBookPro15,1`, `MacBookPro15,3`, `MacBookPro16,1`, `MacBookPro16,4` | Need the patched `amdgpu`, `t2gmux` wiring, the hybrid/dGPU apps and the 16,1 kernel-arg exception |
| Deferred (different machine class) | `MacBookAir8,1`, `8,2`, `9,1`, `iMac20,1`, `iMacPro1,1` | No Touch Bar, iMac ASPM exception, suspend/RTC story unproven off-portable |
| Out of product (no TODO) | `MacBookPro13,x` and earlier, `MacPro*`, `Macmini*` | No T2. The product's own boundary, and today the design never states it |

The four-part argument for the 13-inch class, each part from the evidence base rather than from
analogy:

1. **Same GPU class, therefore same module set.** KAIT2EN's patched-`amdgpu` step is gated to
   `MacBookPro15,1|MacBookPro16,1|MacBookPro16,4|iMac20,1|iMac20,2` and exits early otherwise
   (`research/findings/kait2en.md:157-158`). All four 13-inch models are excluded from that list,
   i.e. on all four the dGPU story is "no device", exactly as the design already says for
   `t2gmux` on 16,2 (`docs/designs/kait2en-bluefin.md:192-193`).
2. **Same Touch Bar class, and the gate is already written as a class.** KAIT2EN's own predicate
   is `MacBookPro15,* || MacBookPro16,*` with the comment that every T2 MacBook Pro has a bar and
   the Air, mini, iMac and Mac Pro do not (`research/KaiT2en-Fedora/scripts/fedora/lib.sh:126-133`).
   The design's single runtime gate (`docs/designs/kait2en-bluefin.md:282`, `:322-324`) is a class
   gate already.
3. **Audio needs no per-model work.** KAIT2EN ships a DSP profile for every model in
   `MacBookPro15,x`/`16,x`, selected by udev from DMI at runtime, with the explicit property that
   "there is no install-time PCI detection" and unsupported models simply receive no graph
   (`research/KaiT2en-Fedora/dsp/config/models.json`, `dsp/README.md:16-23`). The design already
   copies all profiles into the image (`docs/designs/kait2en-bluefin.md:260`), so 15,2/15,4/16,3
   get correct audio for free.
4. **No kernel-arg exception applies to any of them.** The complete exception set upstream is
   `iMac*` (ASPM breaks the Ethernet controller) and `MacBookPro16,1` (Navi 14 drops off the bus)
   (`research/KaiT2en-Fedora/scripts/fedora/install-kernel-args.sh:80-116`). The design ships the
   11 base args with "no model exceptions"
   (`docs/designs/kait2en-bluefin.md:256`, `:321`). That is currently true *because* scope is
   one model; it is also exactly true for the other three 13-inch models, and true for nothing
   else in the T2 fleet.

Firmware does not enter the argument at all, and that is the point: the kit derives the file names
from what the kernel asked for at runtime (`docs/designs/kait2en-bluefin.md:394-396`,
`research/findings/kait2en.md:433-440`). The firmware channel is per-machine by necessity, so it is
model-generic for free. **The expensive parts of this product were already general; only the
release claim was narrow.**

What v1 must add to earn the claim (all inside the blast radius, all under a day, four files):

- A supported-models table in the design, replacing the implicit single-list reading of "named set
  with expected absentees" (`docs/designs/kait2en-bluefin.md:192-193`, `:473-475`) with a
  per-model expected-absent map.
- Correct the two statements whose *reason* expires the moment scope widens: the scope decision
  (`:110-111`) and the app-exclusion rationale, "their model gates exclude MacBookPro16,2"
  (`:233`). On a 15,1 those apps are precisely the ones needed; the reason must become "dGPU
  models are out of v1".
- Static class-A assertions in Tier 0, not a HIL matrix: every shipped unit no-ops without its
  device, the DSP map covers all four, and the kargs list contains no per-model branch. These are
  file-content assertions and need no hardware (`:405-431` is already the right harness for them).
- Delete the phrase "no DMI gate has to work at runtime in v1 except the Touch Bar's"
  (`:110-111`): by the design's own text the Touch Bar gate is `ConditionPathExists`, not DMI
  (`:322-324`), so the honest statement is zero runtime DMI gates — which is a *feature* for
  multi-model, not a v1-only concession.

What this decision explicitly does **not** buy: class B, the Air, or the iMacs. Those need a
per-model kernel-args mechanism, and `kargs.d` is static on bootc, so "support every T2 Mac" has a
real engineering price — it is just not the price the plan currently thinks it is.

**The strategic half of the scope decision** (this is the part that matters more than the model
list): a supported-model set is only as good as the mechanism that proves a machine works, and
today that mechanism is one bench in one room. Widening the claim without widening the evidence
would be marketing. Section "10-star product" and taste decision **T1** carry the remedy.

## 10-star product

**The 10-star version: a T2 Mac that installs itself, and then tells you what works.**

Today a T2 Linux install is a sequence of discoveries: does the keyboard survive initramfs, did
Wi-Fi find its firmware, is the bar lit, did the fingerprint prompt appear at the lock screen. The
user finds out by living with it. The plan's answer to that is a HIL rig that produces
`result.json` (`docs/designs/kait2en-bluefin.md:445-480`) — correct, and pointed at the wrong
audience: it tells the *author* the machine works. Point the same assertions at the *user's*
machine as a one-command report and three things change at once: every install becomes evidence,
every unsupported model becomes a named and bounded surprise instead of a bug report, and the
model matrix stops being the author's private knowledge.

Then the second half: the end state of a hardware-enablement layer is not a fork, it is an
upstream. `nvidia` and `zfs` arrive in Bluefin because they are flavours in `ublue-os/akmods`
(`:158-161`). `akmods-t2` as a permanent fork of a daily-moving upstream with no coordination
channel (`:579-581`) is a rebase treadmill that only runs while one person is pushing. A `t2`
flavour in `ublue-os/akmods`, with `bluefin-t2` reduced to a `FROM` derivative plus config, is the
version where the project can outlive its author. The design's own shape — kmods in one artifact,
image in another — is already 80% of that; what is missing is the sentence that says upstreaming is
the destination.

Five adjacent touches that would make a user say "they thought of that" (each 30 minutes to a day,
none required by the current plan):

1. `bluefin-t2 report` replaces `kait2en-firmware-status` (`:400-401`) as the single status
   surface: model, digest, which of the 18 objects loaded, which are expected absent on this model,
   suspend cycles, bar, fingerprint, DSP sink, firmware state — one screen, no scrolling.
2. The same command's `--markdown` output is the shape the bug-report template asks for, so a user's
   first issue is already evidence.
3. A login-time one-line banner only on first boot when something is expected-absent-by-model, so
   "t2gmux unbound" never again looks like a failure.
4. The kit prints the captured firmware's chip and board (`brcmfmac<chip>-pcie.apple,<board>`)
   before writing the USB — the one moment the user can catch a wrong capture cheaply.
5. The supported-models table ships *in the image* (`/usr/share/bluefin-t2/MODELS.md`) so the
   answer to "will it work on my machine" is on the machine.

## TASTE DECISIONS

Four genuinely close calls. Each needs the human at the final gate; none is a preference of mine
that evidence settles.

1. **Does the user-side validation report ship in v1?**
   *Real tradeoff:* shipping `bluefin-t2 report` in v1 (a report-only command plus a docs page and
   an issue template, ~3–4 files, no new infrastructure) turns every early install into evidence
   and is the only mechanism in this review that makes the multi-model claim provable by anyone but
   the author. Against it: v1's only validated machine is the author's, so the command's first real
   use is on an unvalidated model — meaning v1 is where it is most useful and least proven, and a
   report that itself is broken becomes a second bug in every bug report. My recommendation is
   ship it, report-only, with no upload and no telemetry.

2. **How is the supported set described in public?**
   *Real tradeoff:* "Supports the 13-inch Touch Bar T2 MacBook Pros (validated on MacBookPro16,2)"
   is what makes the product real for someone holding a 15,4, and it is honest only if the shared-code
   argument (the four parts above) is written into the design where users can read it. Against it:
   "Validated on MacBookPro16,2; 15,2/15,4/16,3 expected to work" keeps every claim hard-backed and
   costs nothing but market — and hardware projects that overclaim model support do not get a second
   chance with the people who believed them. Both are defensible; they differ in what happens to the
   first 15,4 user.

3. **Rebuild cadence against HIL capacity.**
   *Real tradeoff:* daily rebuilds against Bluefin keep the kernel and the modules in lockstep, which
   is the whole hazard the design exists to manage, and "a stale image is worse than none because the
   kernel moves underneath it" is correct (`:512-513`). Against it: one Tier 2 run per image change
   at daily cadence is seven full external-disk installations a week on one bench by one person, and
   the plan's own 15–20 minute figure does not include an install, a first boot and a smoke test.
   The options are daily build plus a HIL gate that slips (and then the gate is not a gate), or a
   slower build cadence that the gate can actually cover. Not my call to make on one operator's
   calendar.

4. **Secure Boot in v1: sign and enrol, or document "off"?**
   *Real tradeoff:* the design commits to signing with one key and MOK enrolment from the live
   environment before first boot (`:107-109`, `:194-205`), which is the right end state and is why
   success criterion 2 is written in three states. Against it: the author's own machine runs with
   Secure Boot disabled (`:14`), upstream KAIT2EN ships nothing signed and instructs users to set
   Secure Boot to "No Security" (`research/findings/kait2en.md:35-36`), and enrolment is the one
   install step that can leave a machine with no initramfs keyboard. A v1 that documents "Secure
   Boot off, signed modules are the v2 story" defers key custody, DER shipping, the `policy.json`
   append and the whole enrolment test matrix intact — and removes the most dangerous step from the
   route the product is judged on.

## USER CHALLENGES

Three premises I believe are wrong. The human decides; I did not stop for them.

1. **Assumption:** "v1 supports MacBookPro16,2 only … so no DMI gate has to work at runtime in v1
   except the Touch Bar's" (`:110-111`, `:321-324`).
   **Why it is wrong:** the narrow scope is presented as an engineering economy it does not buy. The
   Touch Bar predicate upstream is already a class (`MacBookPro15,*|16,*`,
   `research/KaiT2en-Fedora/scripts/fedora/lib.sh:126-133`); the DSP map already covers 13 models and
   selects at runtime; the firmware path is machine-generic because it has to be; and no kernel-arg
   exception touches a 13-inch model. Almost nothing in v1 becomes simpler because the claim is one
   model — the design's own unit inventory, DSP set and app list are unchanged either way. The
   saving is in *validation tone*, not in engineering.
   **Cost of proceeding:** the product ships as a one-machine port, which is the opposite of the
   stated intent (`:123-127`). Worse, the model-generic machinery — the udev selection, the
   `ConditionPathExists` no-ops, the per-model expected-absent set — gets no assertion anywhere, so
   the first 15,4 or 16,3 owner is not a supported user, they are a debug session, and the answer to
   "will this work on mine" stays unanswerable for the life of the project.

2. **Assumption:** the kit route's firmware prerequisite is a detail of Constraint 3 rather than a
   property of the product (`:37`, `:353-365`, `AGENTS.md:24-26`).
   **Why it is wrong:** route 1 is the headline route and the only one with "external hardware:
   none" (`:358-361`), and it runs entirely on macOS. So "no external hardware" silently means "no
   external hardware *if your T2 Mac still boots macOS*". A machine whose macOS partition was wiped,
   or which was sold with Linux already on it, cannot use the route the product is built around and
   must fall back to route 2 — which needs an external keyboard (`:363-365`), the exact thing this
   design exists to remove.
   **Cost of proceeding:** the first support thread is a user who followed the docs, found the kit
   cannot run, and has no idea why; and nobody has written the 30–90 minute "reinstall macOS first"
   recovery that the answer needs. Stating the precondition costs one paragraph and reframes route 2
   from "the degraded path for people already on Bluefin" to "the path for machines without macOS".

3. **Assumption:** the validation policy is affordable — daily rebuild (`:512-513`) plus one Tier 2
   run per image change (`:554`) at 15–20 minutes per cycle (`:487-488`).
   **Why it is wrong:** Tier 2 is not a 15–20 minute operation. Per the plan's own description it is
   a containerised `bootc install to-disk` onto an external NVMe, a first boot, an 18-object load
   assertion, Wi-Fi, Touch Bar as the desktop user, fingerprint, one suspend/resume cycle, and a
   power-off (`:445-480`) — with a human physically attaching and detaching disks at both ends. Seven
   of those a week, plus a Tier 3 full kit install per ISO build (`:482-485`), is a full-time bench
   operator's schedule, not a release gate for a project with one operator. When the gate cannot run,
   the honest outcome is that the next release ships without it — and then the plan's strongest
   property, that a bad kernel never reaches a user, is gone silently rather than by decision.
   **Cost of proceeding:** the plan promises a guarantee (`:551-555`) whose staffing model does not
   exist. Either the cadence comes down to what the gate can cover, or the gate becomes a statement
   of intent. Deciding which, now, is cheaper than discovering it at the third kernel bump.

## Deferred to TODOS

Pushed out of v1 by this review, with the reason. Nothing here is rejected as bad work; each is
deferred because it is outside the blast radius, needs hardware that does not exist yet, or solves a
problem v1 does not have.

1. **Per-model kernel-args mechanism** (first-boot `rpm-ostree kargs` with a reboot, or a
   model-conditional bootloader drop-in). Deferred: class A needs no exception, and `kargs.d` is
   static on bootc — this is the gate on class B, the Air and the iMacs, and it needs a design
   decision plus a probe on a real deployment. Owner: eng review.
2. **Class B (dGPU) enablement**: prebuilt patched `amdgpu`, `t2gmux` wiring, the hybrid/dGPU apps
   (`t2-hybrid-gpu-control`, `t2-dgpu-control`) and the 16,1 ASPM exception. Deferred: doubles the
   module count, adds 11 patches to track per kernel, and cannot be validated without a 15-inch
   machine on the bench.
3. **Air / iMac / iMac Pro support**: no Touch Bar, iMac ASPM exception, no suspend parity story, and
   the in-kernel `hci_bcm4377` DMI board table does not list these models
   (`research/findings/kait2en.md:437-444`). Deferred: different machine class, and the Bluetooth
   gap is an upstream-kernel question rather than ours.
4. **Upstream a `t2` flavour into `ublue-os/akmods`** to end the fork. Deferred: coordination work
   with a third party, deliberately out of v1's control; but the design should name it as the
   destination so the fork stays upstream-compatible (L12).
5. **A second HIL target** (a 13-inch 2019, i.e. 15,4 or 15,2) to convert the class-A claim from
   inferred to evidenced. Deferred: needs hardware, and the ordering is "v1 works on 16,2 first".
6. **A no-macOS firmware path** (accept a user-supplied firmware directory, or capture on a second
   machine). Deferred: route 1's precondition is macOS and saying so is enough for v1; the
   workaround is documented, not engineered.
7. **GNOME shell `gresource` / black lock screen** (`:521-522`). Deferred: cosmetic, and it
   overwrites a gnome-shell-owned file — the risk/reward is wrong for v1.
8. **`rpm-ostree initramfs-etc --track` probe** for per-machine ACPI overrides (`:519-520`, `:317-319`).
   Deferred with the design: v1 ships no ACPI overrides, and one probe should settle it before v2
   relies on it.
9. **Review-detail items that belong to the eng review, not the CEO gate**: Secure Boot state (c)
   procedure (R2-7), the polkit helper's exact D-Bus shape (R2-9), the no-marker branch's record
   location (R2-11), and the pipeline race between the two builds (R2-13). Carried forward, not
   dropped.
