## Verdict

**This plan has no user-facing documentation and no contributor on-ramp, and it says so on
purpose.** `:510` states "No DX in v1", and the plan delivers exactly that: a release asset with a
checksum, no page a stranger can read, no repository to fork, no CI, no issue template, no
per-module build target, and twelve kmod specs whose home in the fork base does not exist.

The engineering is not the problem. The kit already contains two of the best developer-experience
artifacts in this entire evidence base: a typed confirmation that refuses by naming itself
(`prepare-fedora-installer.sh:594-610`) and a firmware-capture failure that names cause, fix and
escape hatch in one sentence (`:167`). The plan then keeps the first, keeps the second, and writes
nothing that connects a stranger to either.

Two consequences:

1. **Persona A's install has no entry point and no exit.** No page, no prerequisite box, no version
   on the kit, no receipt at the end. The destructive tool is careful in the middle and silent at
   both ends.
2. **Persona B's path dead-ends at day one**, not because the work is hard but because the plan asks
   a contributor to add twelve specs to a fork whose build model has no place to put a spec and no
   way to build one module.

**Overall DX: 2/10.** With the eight on-ramp steps and the four highest-priority pages below, this
plan reaches 7/10 without adding a feature to the product or a decision to the design.

## Which persona is under-served

**Persona B, the contributor, by a wide margin.**

Persona A has real craft waiting for them and a known set of Phase 2 gaps: the confirmation, the
firmware error, the ESP verification with `cmp` (`:673-675`), the route table. Her problems are
concentrated at the two ends of the journey (no page in, no receipt out) and both are copy.

LICENSE, no README at the project root (`ls` of the working tree: `AGENTS.md`, `CLAUDE.md`, `docs/`,
`research/`, `.gstack`). The one artifact that would make a stranger productive, a single spec that

## Empathy narratives

**Persona A, install night.** I read the release notes on GitHub because that is where the download
is. There is a checksum and a file called something like `install-bluefin-t2.sh`. The notes say to
verify a cosign signature. I do not have cosign. I have `shasum`, which came with the laptop, and
there is a hash in the release notes, so I check that and tell myself it is fine. I run the script
and it asks for my password, then tells me Secure Boot is not disabled and gives me four steps to
disable it, which contradicts the release notes that said the installer enrols a key. I pick my USB
stick from a numbered list. It shows me the name and the size, which is more than macOS gives me. I
type `ERASE disk4`. Then it goes quiet for what feels like ten minutes while it downloads something
and then quiet again while it writes. No bar, no percentage, no "still working". I genuinely do not
know whether it has hung. Then it says done and tells me to sign in to Fedora, which is not the
product I installed. I reboot, hold Option, pick EFI Boot, and the keyboard works in the installer,
and that is the best moment of the whole night and nobody told me it was coming. After the install
there is a blue screen asking me to enrol a key and I do not know what happens if I say no. I log in
and nothing happens at all. I open the app grid and there are six windows called T2 something, and
no Wi-Fi icon. *Predicted, from plan text and kit source. The cosign step, the silence between

the path is written down. **The benchmark target this review sets is therefore not "beat t2-atomic's
four steps". It is "every step the product actually needs is a step a stranger can see".**

- Persona A: from opening the release page to the machine telling them what works.
- Persona B: from "I want to help" to "a signed `t2smc` verified against Bluefin's kernel".

## The kit's CLI, assessed as a product surface

The kit is the only artifact a stranger runs, it runs as root, and it destroys data. That is the
whole case for reviewing it harder than the rest.

### What is already right, and should be kept without argument

- **The confirmation.** `ERASE disk4` is a phrase that cannot be typed by accident, the refusal
  names the phrase it wanted, and the retry tells you Ctrl-C is how to back out (`:594-610`).
  Nothing in this review improves on it.
- **The refusal to be an internal-disk eraser.** `Internal` from `diskutil` is checked twice, once
  when listing and once after selection (`:308-334`, `:470-476`).
- **Verification before and after the write.** ISO volume label checked before `dd`, written label
  and magic checked after, every ESP file checked with `cmp` (`:514-545`, `:624-676`).
- **One error message that is the template for all the others.** `:167`: names the cause, names the
  fix, names the escape hatch.
- **The `--reuse-media` recovery loop.** A failed ESP mount tells you to reconnect and retry with
  `--reuse-media` (`:648-650`). That is a failure that hands you the next command.

### What is missing, ranked by the damage it does

1. **No `--version`, and no coupling between kit release and ISO release.** The kit verifies the ISO
   against a size and SHA baked into `installer-editions.tsv`. Retarget that table to our ISO and
   kit-1.0 plus ISO-1.1 becomes a hard failure whose message blames the user: *"the ISO is not one
   of the supported, unmodified Fedora desktop images"* (`:462-464`). A user who downloaded both
   from the same releases page has done nothing wrong and will be told they have a corrupt ISO.
2. **No `--check`, no `--dry-run`, nothing that runs without writing.** For a root tool that erases
   a disk, "show me what you are about to do" is not a luxury, and it is also the only way Tier 0
   can ever cover the kit's logic. Today the kit cannot be tested without a Mac and a real stick,
   which is why `:482-485` makes Tier 3 the *only* gate on it.
3. **No progress during the two long operations.** The download prints per-mirror lines; the `dd`
   prints nothing at all (`:612-622`). On a slow stick this is 20 minutes of silence with the user
   wondering whether to pull the cable, and pulling the cable is the one action that turns a stick
   into a brick.
4. **No exit-code contract.** `die()` is exit 1, usage errors are exit 2, everything else is
   `on_error`'s "command failed at line 309 (status 1)" (`:70-78`), which is a message written for
   the author and printed to the user.
5. **No preflight for the three prerequisites that actually stop people**: is there a USB stick
   attached and is it big enough for the ISO (checked late, `:509-511`), is Wi-Fi on in macOS (which
   is what makes the firmware capture possible at all), and does this Mac still boot macOS.
6. **Interrupted writes have no recovery page.** Re-running after an interrupted `dd` is safe
   in principle, but the user does not know that, has no command to run, and the tool's own advice
   does not exist for this case.

### The `--help` this kit should print

The current help is eight flag lines with no examples (`:33-47`). A ten-line rewrite buys most of
the CLI score:

```
Usage: install-bluefin-t2 [options]

  Prepares one USB stick on macOS so a T2 Mac can install bluefin-t2
  with its own keyboard and trackpad. It erases the stick you choose.

  --check              Check only. Verifies the ISO, captures the firmware,
                       prints the plan. Writes nothing.
  --disk /dev/diskN    Target the stick directly (still asks for ERASE diskN).
  --firmware-dir DIR   Use Apple firmware from DIR instead of reading macOS.
  --iso FILE           Use an already-downloaded image.
  --reuse-media        Finish a run that stopped part way through.
  --version            Print the kit version and the image release it supports.
  -h, --help

  Requirements: a T2 Mac that still boots macOS, Wi-Fi on in macOS, a USB
  stick of at least 4 GB. The kit prints the four firmware files it captured
  before it writes anything, because they exist only while macOS does.

  Docs: https://.../bluefin-t2#install   Recovery: .../RECOVERY.md
```

## The 12 kmod specs: what a contributor needs and the plan does not say

The plan calls this "the bulk of the estimate" (`:169`) and describes it as an act of writing: 12
specs, one per DKMS package name, each carrying KAIT2EN's `dkms.conf` version (`:169-178`). That
framing is a quantity. The work is a structure.

**Ten things a contributor needs, none of which the plan states:**

1. **Where the spec lives.** `akmods` has no directory for a module's own packaging. Its specs are
   `ublue-os-akmods-addons` and two siblings, all *addon* packages, not kmods
   (`build_files/common/ublue-os-akmods-addons/`). A kmod arrives as `dnf install akmod-xpadneo`
   from a repo (`build-kmod-xpadneo.sh:11`). So the fork must either add a specs directory plus a
   build step, or create a repo or a COPR project. The plan states neither (`:169-178`).
2. **Which build mechanism.** The plan says `akmods --force --kernels <kver>` (`:173`). The one
   worked example in the tree is `rpmbuild` against a fixed kernel release
   (`build-input-kmod.sh:78-86`, `kmod-kait2en-input.spec`). Both work. Picking one is a decision
   the plan owes the contributor, because it decides whether the contributor gets the daily kernel
   chase for free (akmods) or gets a per-module iterate-in-a-minute loop (rpmbuild).
3. **A template.** There is no `kmod-*.spec.in`. The closest is KAIT2EN's installer-transition
   package, which hard-codes five modules, a fixed kver and a `updates/kait2en` install path. A
   contributor can copy it, and copying it teaches the wrong thing twice: no `kmodtool`, no
   weak-modules handling, no per-kver `Requires`.
4. **That the twelve do not share one build contract.** `modules/t2smc/dkms.conf` passes
   `KERNEL_SRC`/`KERNEL_RELEASE`; the other eleven pass `KDIR`/`KVER`. `t2bce_stack` sets
   `MAKE[0]="make KVERSION=..."` through a subdirectory tree and produces five objects;
   `t2touchbar` produces three. "One spec per DKMS package, written once and copied" is false, and
   the plan's own table shows the divergence without saying it is a trap (`:179-186`).
5. **How to build exactly one module.** `just build` builds a *group* (`Justfile:284-333`,
   `images.yaml:1-6`). Twelve modules in one group is a 15-40 minute loop for a one-line change. The
   plan's "review stays per-module" (`:175`) has no build-time counterpart at all.
6. **Which kernel the kit's five modules are built against.** The kit's transition kmod is pinned to
   *the ISO's* kernel (`targets/fedora-44.conf`: `ISO_KERNEL_RELEASE="6.19.10-300.fc44.x86_64"`),
   while the image runs `7.2.5-200.fc44` (`:19-20`) and the author's host runs `7.2.11` (`:13-14`).
   Three kernel versions are in play. The plan mentions the image kernel and the host kernel and
   never mentions the third, which is the one the kit artifact needs.
7. **Where a per-kernel compat patch goes when the patch is per-module.** The plan mirrors
   `patches/fedora-44-input.patch` (`:176-178`). That patch applies to a bundle of five modules.
   Per-spec patches mean twelve patch lifetimes, and the plan's review practice is
   per-spec. Nobody has written down what happens when two specs need the same patch.
8. **How to test a spec without publishing.** No COPR, no repo, no local-only path. The `mock` and
   `rpmbuild` tools are in the build container already (`build-prep.sh:50-56`), so the loop is
   cheap once someone says what it is.
9. **That a local build already gives you a test key**, and that the warning which tells you about
   it points at a script that is not in the tree (`build-prep.sh:57-61`). A contributor's first
   sign-related message is a dead end.
10. **The one-spec-per-PR path.** The plan asks for per-module review (`:175`) and gives no process:
    no template PR, no review checklist, no order to write them in (dependency order matters:
    `t2bce_dma` before `t2bce_core` before `t2bce_vhci`).

**Minimum fix, and it is small:** one template spec (`kmod-t2.in`), one `just` target that builds
and signs a single module for a given kver, one page of traps (items 1, 2, 4, 6 above), and a
dependency order for the twelve. That is a day of work that converts the plan's largest estimate
item into twelve independent PRs.

## The supported-model contract, assessed as a docs artifact

Phase 1 recommends claiming the four 13-inch integrated-GPU Touch Bar models and validating one
(`01-ceo.md`:54-99, T2 `01-ceo.md`:214-221). That claim is only honest if the shared-code argument is
written where a user can read it, and Phase 1 says so. This review adds three things Phase 1 did not
say about it as an *artifact*:

1. **It is not a marketing page, it is the contributor's add-a-model rubric.** The four parts of
   Phase 1's argument are: same GPU class so the same module set; the Touch Bar gate is already a
   class predicate; the DSP map already covers every model and selects at runtime; no kernel-arg
   exception applies. Every one of those is a *testable condition a new model must satisfy*. Written
   as a support claim it answers "will it work on mine". Written as a checklist it also answers
   "what would I have to prove to add mine", which is exactly the missing precursor to Phase 1's
   deferred multi-model work (`01-ceo.md`:294-319). Same words, two audiences, and the plan contains
   neither.
2. **A support claim without a per-model test recipe is unverifiable by the person it is aimed at.**
   The claim needs one line per model: validated / supported-by-argument / unknown, plus the
   expected-absent set for that model, plus the exact command that proves it on their machine. Phase
   2's `report` exit code 2 (T4 of `02-design.md`) is the command. Without the pairing, the model
   table is a promise and the report is a diagnostic, and neither closes the loop.
3. **It has to ship inside the image, not only on the web.** The machine with no Wi-Fi cannot read
   the web page. `/usr/share/bluefin-t2/MODELS.md` (Phase 1's touch 5, `01-ceo.md`:163-164) plus
   `RECOVERY.md` in the same directory is the only form that survives the product's own worst state.
   `02-design.md` T6 already carries this; this review only records that it is a *DX* requirement
   and not a nice-to-have, because the page is the product's only self-description at the moment the
   user needs it.

**Verdict on the docs artifact: 2/10 as specified, 7/10 if written as a table plus a rubric plus a
proof command.** The content exists in `01-ceo.md`. It has no home.

## The contributor on-ramp

The minimum sequence to make a stranger productive, in order. Steps 1-4 are a day. Steps 5-8 are
the difference between "someone could" and "someone did".

1. **A repository with an identity.** `git init`, public, `README.md`, `LICENSE`
   (GPL-3.0-or-later per `:495-498`), the shipping name `bluefin-t2`, one paragraph of what it is,
   and a link to the design doc. This is not a codebase. It is the thing that makes the next seven
   steps addressable.
2. **`CONTRIBUTING.md` with the first-day path and the hardware honesty.** Named prerequisites
   (Linux x86_64, podman; **not** a Mac, per `:100`), the devcontainer one-liner that already works
   (`research/akmods/README.md:183-203`), the eight steps to a signed module, and a section that says
   plainly which of the nine verification steps a contributor without a T2 Mac cannot do. Stating
   the limit is worth more than hiding it: it is the reason a contribution is reviewable at all.
3. **One template spec plus one per-module build target.** `just module t2smc 7.2.5-200.fc44` that
   builds, signs and verifies a single `.ko`. Reuse `build-input-kmod.sh`'s rpmbuild pattern as the
   worked example (it is the only one in the tree) while keeping `akmods --force` for the published
   path. This is the decision TD3 asks for; whichever way it goes, the target is the deliverable.
4. **`ADD-A-MODULE.md` with the four traps.** The template, the twelve-module dependency order, the
   `KERNEL_SRC` versus `KDIR` divergence, the three-kernel rule (host, image, ISO), and where a
   per-module patch goes.
5. **The `t2-test-harness` image, or a documented `podman run` that reproduces Tier 0 locally.**
   `:405-410` already names its contents. Without it, Tier 0 exists only in CI that does not exist,
   and a contributor cannot run the gate they are asked to pass.
6. **CI on PR: Tier 0 plus the fail-closed tag check.** The tag check is R2-13's remedy and it is
   also a contributor-facing message: it is what stops a PR from being merged into an image that
   cannot build.
7. **Issue templates: bug (`report --markdown`), model report, add-a-model request, module
   proposal.** Four templates, and the first one is free because Phase 2's `report` already writes
   the body.
8. **A bench note: what a contributor without hardware can and cannot prove**, and the one-line
   warning that unloading `t2hid`, `t2bce_*` or `hid_t2magicmouse` locks the machine out
   (`:433-441`, `AGENTS.md:21-23`). This warning lives in the project contract and not in the repo
   anyone will fork, which means the person most likely to need it will never read it.

**Sequencing note.** Step 1 and step 2 need no technical decision and can happen this week. Steps 3
and 4 need TD3 answered. Steps 5-8 need the repo to exist. Nothing in the sequence needs the module
pipeline to work first, which means the on-ramp can be built in parallel with Artifact 1 rather than
after it.

## NOT in scope, with reasons

1. **A docs site, versioned multi-page portal, or search.** Nine markdown files in a repo is the
   complete answer at this stage; a site is a maintenance surface with no reader.
2. **Any telemetry or install-time reporting.** Correctly excluded by `02-design.md`, and this review
   would argue against adding it even if offered: hardware-enablement state is not something to
   phone home about.
3. **A Mac-side full image build.** Premise 6 (`:100`) stands. Only single-module builds are
   proposed as a Mac-capable path (TD4).
4. **Rewriting the kit's flow.** The middle of the install is the best-designed part of the product.
   Everything this review asks for the kit is additive: `--version`, `--check`, progress, a preflight,
   a receipt.
5. **Converting `research/` clones into a fork or a submodule here.** `AGENTS.md:13-14` says
   read-only, and the plan already pins KAIT2EN as a submodule (`:582-583`).
6. **The module pipeline, CI mechanics, signing cryptography and the `akmods-t2` fork shape.** Phase
   3's. This review names the contributor-facing surface of each and leaves the mechanism alone.
7. **The first-login surface, the hub and the Touch Bar lesson.** Phase 2's G1/G4/G5. This review only
   requires that whatever ships has a page behind it.
8. **Multi-model support.** Phase 1 deferred it (`01-ceo.md`:294-319). Page 1 states the claim; it
   does not widen it.

## TASTE DECISIONS

Five genuinely close calls. Each needs the human at the final gate; none is settled by evidence.

### TD1 — Is the download verified with cosign, or with a hash macOS already has?

*Real tradeoff:* the plan says SHA-256 **and** a cosign signature (`:503-505`), which is the stronger
supply-chain claim and matches the registry-key story at `:499-502`. Against it: cosign is not on
macOS, so the required check becomes `brew install cosign` on the first command a stranger runs, and
people who will not install Homebrew will skip verification entirely. `shasum` ships with the
operating system and verifies the same bytes. **My recommendation is `shasum` as the required check,
cosign published as the optional stronger check**, because for Persona A a check that runs is worth
more than a check that is stronger and skipped. This is the difference between the supply-chain
story being true and being aspirational, and the two halves can be split without losing either.

### TD2 — Does the kit get a `--check` mode in v1?

*Real tradeoff:* `--check` is the only way the kit's logic ever gets Tier 0 coverage, and the only
way a nervous user can rehearse a destructive operation. Against it: it is new CLI surface in a
release the plan scoped tightly, it has to be kept honest forever (a `--check` that drifts from the
real run is worse than none), and every line of it is a line the Tier 3 run does not exercise.
**My recommendation is yes, scoped to the pre-write half** (verify, capture, render, size-check) with
the write explicitly out of its reach, because that half is exactly what Tier 0 can then assert and
exactly what the user is most uncertain about.

### TD3 — Do the twelve specs use `akmods --force`, or the `rpmbuild` pattern that already works?

*Real tradeoff:* `akmods --force --kernels <kver>` (`:173`) is what the plan commits to, it gives the
daily kernel chase for free, and it is the mechanism that makes `akmods-t2` a real thing. Against it:
there is no kmod spec anywhere in the akmods tree, no place to put one, and no per-module build; the
only worked example in the evidence base is `kmod-kait2en-input.spec` plus `build-input-kmod.sh`,
which builds one RPM for one kernel in about a minute and has already been used in anger. **My
recommendation is the rpmbuild template for the contributor loop and `akmods --force` for the
published artifact**, with `ADD-A-MODULE.md` saying both and which one to run when. It is the only
shape where a contributor's iteration is fast and the release path stays in lockstep. This is the
decision that changes a contributor's first day.

### TD4 — Is the T2 Mac allowed to be a build host?

*Real tradeoff:* premise 6 (`:100`) excludes the Mac because the image build is 30-60 minutes and
20 GB (`:89`). It does not follow that a *single module* cannot be built there: the author's machine
already compiles DKMS modules against its own kernel as normal operation, and Tier 1 (`:433-441`)
is written for exactly that. Allowing it doubles the contributor pool to include the people who own
the hardware. Against it: two build environments to document, and a Mac build against `uname -r`
produces a module that will not load on the image, which is the exact confusion the whole design
exists to prevent. **My recommendation is to document it narrowly**: the Mac may build for Tier 1
verification only, the page says the vermagic will not match the image, and the image kernel stays a
container-only build.

### TD5 — Do the nine docs pages ship before Tier 3 or after?

*Real tradeoff:* writing them before Tier 3 means the docs act as the spec (the discipline that
produced the plan's best sections) and the release has them on day one. Against it: any page
describing a screen that Tier 3 found inoperable becomes a lie shipped to users, and the enrolment
screen and the first-login surface are both undesigned (Phase 2 step 7, G1). **My recommendation is:
write pages 1, 4 and 9 before Tier 3 because they describe behaviour that already exists, and write
pages 2, 3, 7 and 8 immediately after the first green Tier 3 run**, describing only what it
exercised. That serialises three days against the release, which is the honest cost of not shipping
fiction.

## USER CHALLENGES

Three premises I believe are wrong. The human decides; I did not stop for them.

### U1 — A signature is not a safety story

**Assumption:** "No `curl | bash` for a tool that rewrites an ESP. Publish the kit as a release asset
with a SHA-256 and a cosign signature; the documented command downloads, verifies, prints the target
disk and requires a typed confirmation" (`:503-505`) is the answer to shipping a destructive tool.
**Why it is wrong:** three of those four clauses are about *provenance*, and provenance is not where
this tool hurts people. The ways a T2 owner loses data here are: the wrong disk (mitigated well,
`:594-610`), an interrupted write (not mitigated at all, U2), and a kit from the wrong release run
against a newer ISO (actively misleading, U7). None of those is a supply-chain problem and none is
touched by cosign. The kit has no `--version`, no `--check`, no progress while writing and no
post-failure recovery, which is the complete list of what a destructive tool owes a cautious user.
**Cost of proceeding:** the project ships with its supply-chain story told and its data-loss story
untold, and the first support thread is a half-written stick and a message that blames a good ISO.

### U2 — "Twelve specs" is a quantity, and the wall is structural

**Assumption:** the module packaging is "the bulk of the estimate" (`:169`) because there are twelve
of them and none exists.
**Why it is wrong:** `ublue-os/akmods` contains **zero kmod specs**. Every kmod it builds is an
`akmod-*` RPM fetched from COPR, Terra or negativo17 (`build_files/common/build-kmod-xpadneo.sh:11`,
`README.md:47-72`), and its own documentation for adding a module is "file an issue asking about
inclusion" (`README.md:259-266`). So "fork akmods and write twelve specs" crosses a boundary the
plan does not name: the specs need a repo, a COPR project, or a new build path, and each of those is
either a third party outside v1's control or a piece of the fork that does not exist. Twelve is not
the cost. Finding the place for the first one is.
**Cost of proceeding:** every contributor's first evening ends at the same wall, the plan's "one
spec per PR, review stays per-module" (`:175`) has no build-time counterpart, and the largest
estimate line item is a week short because the estimate priced writing, not placement.

### U3 — The kit is released as an asset, but nothing about it is releasable

**Assumption:** the kit is "released as an asset from the same repo" (`:160-161`, `:503-505`), so it
is a build output like the image.
**Why it is wrong:** the kit runs on an operating system the build never touches, as root, against
real hardware, and it is the only artifact a stranger executes. It cannot run in Tier 0 (no macOS),
cannot be rehearsed (`--check` does not exist), cannot be traced to a version (`--version` does not
exist), and cannot be tested without a Mac and a stick, which is why `:482-485` makes Tier 3 its only
gate. An unversioned, untestable, root-executed script is not a release asset. It is a hotfix stream
with no channel.
**Cost of proceeding:** every support conversation opens with "which kit did you run", there will be
no answer, and the one part of the product that can destroy data is the part with the least
verification. The remedy is not large (`--version`, `--check`, the release coupling from U7) but it
has to be in v1, not after it.
