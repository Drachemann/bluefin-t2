## Verdict

**The architecture is right and the sequence is wrong.** The three-artifact split (kmods artifact,
thin image, kit), the `FROM` derivative that owns its own dracut, the akmods tagging convention, and
the named-set assertion style are all correct and all supported by the evidence base. What is not
yet true is that this plan can be built in the order it states and fail loudly when it is wrong.

Six of the sixteen carry-forward findings are still open in the body, and four of those are not
documentation gaps: they are mechanisms that do not work as written.

- **R2-13** has no kernel resolution and no fail-closed behaviour. A daily-cadence image build can
  run against a module cache that does not exist, and nothing in the plan stops it.
- **R2-3** is worse than "unassigned": the plan's own evidence base states that the live carrier
  does not reach the installed system (`auto-installer/initramfs/90-kait2en-updates.sh:11-14`, "Nothing
  placed here reaches the installed system"), the kit runs on macOS and never touches the target
  disk, and R2-3 is a launch blocker for the only route with the "no external hardware" claim.
- **R2-7** has no enrolment step on route 2, so the documented path for a machine without macOS
  reboots into modules that will not verify, and the internal keyboard is one of them.
- **R2-9**'s bind unit is inverted: `ConditionPathExists=%h/.config/kait2en/touchid-bound`
  (plan `:284`) fires when the marker exists, and the unit itself creates the marker, so it either
  never runs or runs every login. A user unit also cannot restart a system service.

Four further defects were found in this review and none of them is a restatement of a prior finding:
the kargs count is wrong by one and asserted by count rather than by name; the installer
initramfs list names a DKMS package (`t2touchbar`) as if it were a module; `t2gmux` is asserted to
"load and stay unbound" on MacBookPro16,2 when it does not load at all (verified); and the
build-only package split is asserted rather than made structural.

**Verdict: buildable, not build-ready. 5/10.** With the nine resolutions below, the first
implementable task is unchanged from the plan's own Assignment, and the first four tasks before any
image exists are named at the end of this document. Two things stay unresolved by evidence and go to
the human gate: where the firmware-crossing code lives, and the signing-rotation policy.

## The locked architecture

Four published artifacts, one build host, one HIL bench. The additions from Phases 1 and 2 change
the *contents* of artifact 2 and add data files, not the number of artifacts.

```
                     ghcr.io/ublue-os/akmods:<flavor>-<fedora>      (ublue's, daily)
                          │  label ostree.linux = KVER
                          ├─────────────────────────────┐
                          ▼                             ▼
        [A1] akmods-t2:<flavor>-<fedora>-<KVER>   ghcr.io/ublue-os/bluefin:<fedora>@<digest>
             label ostree.linux = KVER               label ostree.linux = KVER
             + floating tag <flavor>-<fedora>                     │
             cosign: our key                                      │ KVER read from THIS label
                          │                                       ▼
                          └───────────────► [A2] bluefin-t2:<tag>  (FROM bluefin@digest)
                                                  │  asserts: akmods-t2 tag exists for KVER
                                                  │  asserts: kmod Requires kernel-core-uname-r = KVER
                                                  │  dracut regenerated IN the derivative
                                                  ▼
                                    [A3] installer kit (release asset, macOS)
                                                  │  writes payload to the USB ESP
                                                  ▼
                                    [A4] BIB anaconda-iso from A2 (+ kickstart post-script)
                                                  │
                                                  ▼
                                            [A5] HIL results (USB stick)
```

Two rules make this diagram true rather than aspirational.

**Kernel resolution, one direction only.** `KVER` for artifact 2 is read from the *pinned base
digest's* `ostree.linux` label, never from `uname -r`, never from a floating tag, never from the
akmods image. That is the same rule Bluefin itself applies at
`research/bluefin/Justfile:153` (read the label) and `:156` (verify the kver-tagged image), and it is
the reason the label exists: `research/bluefin/Justfile:219` writes it at publish time. Artifact 1
resolves its `KVER` from *ublue's* floating akmods tag label, which is the earliest point in the
chain and the same source Bluefin uses, so A1 is never later than A2 by construction.

**The tag is a name, the RPM dependency is the lock.** The `skopeo inspect` for the
`akmods-t2:<flavor>-<fedora>-<KVER>` tag gives a clean, named error ("no kmod cache for
7.2.5-200.fc44"). The thing that actually prevents a broken image is upstream of that: the kmod RPM
must carry `Requires: kernel-core-uname-r = <KVER>`, which is exactly what KAIT2EN's own transition
package does (`auto-installer/kmod-kait2en-input.spec:13-14`). With that dependency, a mismatch makes
`dnf5 install` fail even if the tag check were deleted. Assert this in artifact 1's Tier 0 with
`rpm -qpR`, and the race stops being a policy and becomes a property.

### Artifact 2, the Containerfile, locked

Nine steps and two stages. The second stage is the change this review makes to the plan's structure.

```
FROM ghcr.io/ublue-os/bluefin:<fedora>@<digest> AS t2build        # builder: compiles only
   B1  dnf5 install build-only set (cargo, rust, gtk4-devel, libadwaita-devel, libinput-devel,
       libplist-devel, systemd-devel, glib2-devel, rpm-build, pkgconf-pkg-config, gcc, make,
       checkpolicy, policycoreutils, selinux-policy-devel)
   B2  COPY pinned KAIT2EN submodule
   B3  build 8 apps + t2remote -> /out/rpms/*.rpm                  (plan step 08)
   B4  checkmodule + semodule_package -> /out/selinux/*.pp         (plan step 09, SELinux half)
   # nothing from this stage reaches the image except /out

FROM ghcr.io/ublue-os/bluefin:<fedora>@<digest>                  # the image
   01  resolve KVER; skopeo copy + cosign verify akmods-t2; unpack; dnf5 install kmod RPMs;
       depmod -a "$KVER"; write modules-load.d + modprobe.d       (plan step 06)
   02  dnf5 install runtime set; rsync system_files/shared/ /      (plan step 07)
   03  dnf5 install /out/rpms/*.rpm                                (plan step 08 output)
   04  semodule -X 400 -i /out/selinux/*.pp; authselect ... with-fingerprint   (plan step 09 rest)
   05  fc-cache -f; gtk-update-icon-cache; dconf update            (plan step 08 caches)
   06  dracut --force --no-hostonly --kver "$KVER" --reproducible --add ostree   (plan step 10)
   07  90-tests.sh   (our gates, replacing Bluefin's 20-tests.sh which is not ours)
   RUN bootc container lint                                        (last, as Bluefin does)
```

Why the builder stage is structural, not stylistic: today the plan installs eighteen build-only
packages into the same filesystem as the image and removes them in a later step (`:216-226`), then
asserts their absence in Tier 0 (`:421-424`). That assertion can only prove the RPM is no longer
registered. It cannot prove the files are gone, and it says nothing about build residue such as a
cargo registry, a `target/` tree or a fetched source tarball. A stage boundary removes the entire
class: nothing the compiler touched exists in the final filesystem. Keep the Tier 0 absence
assertion anyway, as defence in depth, but stop calling it the guarantee.

Two boundary decisions that follow from this table.

- **One harness image, not two.** The plan proposes `ghcr.io/<org>/t2-test-harness` carrying
  `kernel-devel` (`:405-410`). Artifact 1 already has exactly that container, at exactly the right
  kver, because it compiles the modules. Publish it as `akmods-t2:harness` from the same repo with
  the same pin, and Tier 0 runs there against the built image mounted read-only. One fewer published
  artifact, and the harness can never drift from the kernel it tests.
- **One expectation set, three consumers.** `models.d/<ProductName>.toml` holds
  `expected_loaded`, `expected_absent`, `expected_unbound`. `bluefin-t2 report` renders it, Tier 2
  asserts it, and `MODELS.md` is the human prose. This is Phase 2's "one assertion set, two front
  ends" (`02-design.md:574-579`) extended by one consumer, and it is what makes the 18-object
  assertion survive four models.

### The initramfs guarantee, stated exactly

The keyboard before root is guaranteed by four things, and only the fourth is a proof:

1. `usr/lib/dracut/dracut.conf.d/90-t2-input.conf` ships in the image, copied from the live host's
   `/etc/dracut.conf.d/90-kait2en-input.conf` (`research/KaiT2en-Fedora/scripts/fedora/rebuild-initramfs.sh:11-19`),
   `force_drivers+=" t2bce_dma t2bce_core t2bce_vhci t2hid t2smc t2sbs "`.
2. The six objects are installed under `/usr/lib/modules/$KVER/` by step 01, before dracut runs.
3. `dracut --no-hostonly --kver "$KVER" --add ostree` runs at step 06, which is what Bluefin does at
   `research/bluefin/build_files/base/19-initramfs.sh:7-9`.
4. `90-tests.sh` runs `lsinitrd` and asserts each of the six object names is present. **This is the
   proof**, and the plan puts it only in CI (`:416-417`). It must run inside the image build, because
   dracut treats a missing `force_drivers` module as a warning: a typo, an object renamed upstream or
   a stale module path all produce a green build and a machine with no keyboard at the LUKS prompt.

Fallback when a kernel bump breaks a module: the compile fails in artifact 1, no tag is published for
the new `KVER`, artifact 2's tag check fails with a named error, no image is published, users stay on
their previous deployment. That chain is the plan's real safety property and it only exists once
R2-13's resolution is adopted.

### Signing key lifecycle, locked

| Stage | Decision |
|---|---|
| Generation | Offline, one keypair, `signing_key.pem` (private + cert) per `dual-sign.sh`'s format; public DER committed and published as a release asset |
| CI storage | Organisation secret, available only to `push`-on-`main`/tag workflows. Fork PRs cannot sign (GitHub does not expose secrets to them), so contributor PRs build with the test keys already in `research/akmods/certs/` and only releases are signed with the real key. State this, because it is also why "verify the signature" in a PR means "verify against the test key" |
| Shipping | DER at `/etc/pki/akmods/certs/` (the `ublue-os-akmods-addons` convention) and as a release asset for `mokutil --import` |
| Rotation | Additive and overlapping. A second key signs every module **twice** for at least two releases after a rotation, which is what `dual-sign.sh:15-22` already does; the design at `:194-205` explicitly decided not to dual-sign, and that decision is wrong for rotation even though it is right for the kernel (we do not hold the kernel key) |
| Existing users on rotation | Nothing breaks during the overlap. After it, a user who never enrolled the new key loses the modules on the next upgrade. Recovery is the GRUB menu and a rollback, not a reinstall, because the Apple firmware still feeds GRUB its keyboard (`auto-installer/grub.cfg.in:26-27` documents that GRUB receives keys, and only loses Ctrl-X/F10) |
| Detection | `bluefin-t2 report` asserts `mokutil --sb-state` and whether our DER is in the enrolled list, and returns exit 1 with the enrolment command. Without this the failure is silent until a keyboard does not work |

## Resolutions

One subsection per mandatory item. Each states the decision first.

### R2-13: the two-pipeline race

**Decision.** `KVER` is read from the base image's `ostree.linux` label, resolved *before* the
`FROM`; `akmods-t2` publishes both a floating `<flavor>-<fedora>` tag and the immutable
`<flavor>-<fedora>-<KVER>` tag, each carrying `ostree.linux`; artifact 2 verifies the immutable tag
with cosign and fails with a named error when it is absent; the kmod RPM carries
`Requires: kernel-core-uname-r = <KVER>` so a mismatch cannot install; artifact 1 resolves `KVER`
from *ublue's* floating akmods tag, not from `bluefin:stable`.

**Why.** This is Bluefin's own mechanism, verified line by line. `Justfile:153` reads the label from
`ghcr.io/ublue-os/akmods:"${akmods_flavor}"-"${fedora_version}"`; `:156` verifies the
kver-tagged image before use; `build_files/base/03-install-kernel-akmods.sh:18` copies
`akmods:"${AKMODS_FLAVOR}"-"$(rpm -E %fedora)"-"${KERNEL}"`, and `:34` versionlocks the result. ublue
publishes both tags with the label at `research/akmods/Justfile:311-333`. Chasing
`bluefin:stable`'s label from artifact 1 (the plan's `:204-205`) is a day behind reality, because
Bluefin publishes only after ublue's akmods moves; chasing ublue's floating tag removes most of the
race and the tag check removes the rest.

**Trigger order, stated.** (1) ublue akmods publishes `<flavor>-<fedora>` + kver tag. (2) artifact 1
runs: daily cron on ublue's label, `repository_dispatch` on KAIT2EN movement, manual. (3) Bluefin
publishes. (4) artifact 2 runs on cron against Bluefin, or on `repository_dispatch` from artifact 1.
Steps 2 and 3 run concurrently and step 4 can start before step 2 finishes; that is fine, because
step 4 fails closed. No ordering discipline is required anywhere, which is the point: order is a
weaker guarantee than a check.

**Where it is tested.** Tier 0 negative test in artifact 2: run step 01 with a
`KVER` for which no tag exists, assert a nonzero exit and the exact error text. Tier 0 in artifact 1:
`rpm -qpR` on every kmod RPM contains `kernel-core-uname-r = <KVER>`. A second negative test asserts
the image build fails when a kmod RPM for the wrong kver is forced into the unpack directory.

### R2-3: firmware across the install boundary

**Decision.** The payload crosses in the **Anaconda installer environment, not through the kit**,
because the kit runs on macOS and never touches the target disk. Three parts:

1. **The carrier already exists.** The kit writes the firmware as a third initrd
   (`auto-installer/grub.cfg.in:14`, `prepare-fedora-installer.sh:574,669`) and a dracut pre-pivot
   hook copies it to `/run/kait2en/apple-firmware` (`auto-installer/initramfs/90-kait2en-updates.sh:4,12-13`).
   That hook says in its own comment that `/run` survives the switch root for the live session only
   (`:11-14`). So during install the four files are at a known absolute path in the installer root.
2. **The transfer is one post-script inside the updates image.** The kit already ships an Anaconda
   updates image and already passes it (`grub.cfg.in:12`, `inst.updates=file:///run/kait2en/updates.img`;
   built and self-checked at `build-in-container.sh:283,332`). Add
   `/usr/share/anaconda/post-scripts/90-bluefin-t2-firmware.ks` to that image, which
   copies `/run/kait2en/apple-firmware/*` to `/mnt/sysroot/boot/efi/kait2en/firmware/wifi/`,
   verifies `SHA256SUMS`, and writes `/mnt/sysroot/etc/bluefin-t2/firmware-import.json`. No
   `inst.ks=`, no Anaconda Python addon, no new cmdline, and the existing self-check that asserts
   `! grep -Fq 'inst.ks='` (`build-in-container.sh:335`) stays true.
3. **Fail closed.** The post-script runs `--erroronfail`. If the source directory exists and the copy
   or the checksum fails, the installation fails at the point where the cause is still on screen,
   rather than producing a machine with no Wi-Fi and no explanation. If the source is absent (route 2,
   or an unprepped ISO), the install proceeds and first boot reports `absent`.

**Why not the alternatives.** A kickstart `%post` from a BIB `[customizations.installer.kickstart]`
block also works and is proven in this evidence base (`research/t2-atomic/disk_config/iso-bluefin.toml:1-5`,
`research/findings/t2atomic.md:183,216`), but it puts the transfer code in the ISO, so every copy fix
needs an ISO rebuild (30–60 min plus a Tier 3 run). The post-script rides the kit, which is already
versioned and already on the stick. A first-boot copy from the installer medium requires the USB to
stay attached at first boot, which re-introduces the exact hardware-free claim the route is built on.
Reflowing the target ESP from macOS is impossible: the target ESP does not exist yet.

**What is not settled.** Whether the Anaconda version in the BIB ISO runs `updates.img`
`post-scripts`. This is a documented Anaconda mechanism but it is not proven in this tree, and it is
TASTE DECISION TD1 below. Tier 3 must prove it, and the fallback if it does not hold is the kickstart
block (which is proven in t2-atomic), decided at the first ISO build, not at release.

**Where it is tested.** Tier 3, and only Tier 3: after the install completes and before first boot,
mount the target ESP and assert the four files plus `SHA256SUMS`; then boot and assert Wi-Fi
associates. A negative Tier 3 run: delete the payload from the stick after the install starts, assert
the install fails with the named message (this is the fail-closed test).

### R2-7 and route 2: Secure Boot without an enrolment step

**Decision.** Route 2 gets a mandatory enrolment step *before* the switch, performed on the running
stock Bluefin with the external keyboard attached: download the DER, `mokutil --import`, reboot, enrol
in the MOK Manager, then `bootc switch`. Order matters and is part of the documented procedure.

**Why.** `bootc switch` changes the deployment and reboots; there is no pre-boot hook and no way to
enrol from the new deployment, because the new deployment is the one whose modules need the key. MOK
enrolment is a shim-time, pre-boot interactive step, so it must be staged before the reboot that
introduces the modules. The user is already on an external keyboard on stock Bluefin (no T2 modules
exist there at all), so the keyboard requirement is not new; the failure being prevented is the one
where they remove it after the reboot.

**Recovery, and a correction to Constraint 5.** The plan calls this "unrecoverable" (`:81-83`). It is
not: the Apple firmware still feeds GRUB its keyboard, which is why the kit can say "Apple firmware
gives GRUB no Ctrl-X or F10" (`auto-installer/grub.cfg.in:26-27`), so arrow keys and Enter work at the
boot menu even with zero T2 modules. The honest statement is: **the new deployment is unbootable past
the LUKS prompt; the machine is recoverable from the GRUB menu by choosing the previous deployment.**
That recovery ships as a documented procedure and as a line in `bluefin-t2 report`, not as prose in a
design document. What is genuinely unrecoverable is a fresh install with no previous deployment,
which is why enrolment happens in the live environment on route 1 and before the switch on route 2.

**Where it is tested.** Tier 3 for route 1 state (b) and the deliberately-skipped state (c), with the
boot-menu rollback executed and recorded. Route 2 is tested by a scripted procedure on a stock
Bluefin T2 machine, once per release cycle, because it needs a second machine state and the bench has
one.

### R2-9: the Touch ID bind unit, and the inverted condition

**Decision.** Keep a user unit, fix the condition, and ship exactly one privileged helper for all
per-user provisioning.

```
/etc/systemd/user/bluefin-t2-first-login.service
  [Unit]
    Description=bluefin-t2 first-login provisioning
  [Service]
    Type=oneshot
    ConditionUser=!@system
    ConditionPathExists=!%h/.config/bluefin-t2/provisioned     # note the "!"
    ExecStart=/usr/bin/pkexec /usr/libexec/bluefin-t2/provision-user
    RemainAfterExit=yes
  [Install] WantedBy=default.target
```

- **The inversion.** `ConditionPathExists=` is true when the path exists. The plan's unit
  (`:284`) is conditioned on the marker that the unit's own run creates (`:302-305`), so on a fresh
  user it is false and the unit never runs, and once it has run it is true and the unit runs at every
  login forever. `ConditionPathExists=!%h/...` is the correct primitive: run while the marker is
  absent, then create it. Verified semantics: systemd supports the `!` prefix on
  `ConditionPathExists=`. The same review applies to every other new condition in the inventory, and
  the only one that is correct as written is the Touch Bar's, which conditions on a device node an
  external driver creates (`:282`).
- **The helper.** `/usr/libexec/bluefin-t2/provision-user`, shipped with
  `/usr/share/polkit-1/actions/org.bluefin_t2.provision-user.policy`, action
  `org.bluefin_t2.provision-user`, `allow_active=yes`, and **no user argument**: it derives the uid
  from `PKEXEC_UID`, so it can only ever provision the caller. It does three idempotent things:
  write `T2_TOUCHID_BIND_USER=<caller>` into `/etc/kait2en/t2-touchid.conf` and
  `systemctl restart kait2en-t2-touchid.service` only if the value changed; `usermod -aG
  kait2en-touchbar <caller>` (Phase 1 L6's second need, same helper, one first-login event); then
  `install -Dm0600 /dev/null "$HOME/.config/bluefin-t2/provisioned"` as the caller.
  `allow_active=yes` is right rather than `auth_admin`: binding your own account is self-service, not
  privilege escalation, and a polkit prompt from a background user unit has no agent in the general
  case. The security property is the absent argument, not the authentication.
- **First login detection.** The marker plus `ConditionPathExists=!`, in a user unit with
  `WantedBy=default.target`. `ConditionUser=!@system` keeps it out of the greeter's session. It is
  idempotent and re-runs if the user deletes the marker, which is the desired behaviour.
- **Not a second mechanism.** Phase 1 L6 asked for one per-user mechanism, and this is it: Touch ID
  binding, the Touch Bar group, and (if bundled) the first-login report are one unit, one helper, one
  marker.

**Where it is tested.** Tier 0: `systemd-analyze verify`; the unit text contains
`ConditionPathExists=!`; `pkaction --verbose` lists the action with `allow_active=yes`; a grep
asserts the helper reads `PKEXEC_UID` and takes no positional argument. Tier 2: a fresh user's first
login writes the marker and the config, a second login does not restart the daemon, and
`systemctl --failed` is empty.

### R2-11: failed-boot capture

**Decision.** Three monotone artifacts, each written by a different layer, so that the *absence* of
the next one localises the failure:

| Artifact | Written by | When | Proves |
|---|---|---|---|
| `attempt.json` (digest, KVER, SB state, boot target, timeout, run id) | **host harness**, on the K2B-HIL stick | before the machine is powered on | the run existed |
| `stages.log` (one line per stage, append-only, fsync) | `bluefin-t2-hil-early.service` at `sysinit.target`, then at `multi-user.target` | during boot | the kernel and initramfs completed and userspace reached the stage |
| `result.json` (the smoke test) | `bluefin-t2-hil-test.service`, which then powers off | after the smoke test | the run finished and with what outcome |

Outcome table, evaluated by the **host** on the next run, because the machine cannot report its own
pre-Linux failure:

1. `attempt.json` + `stages.log` (2 lines) + `result.json` → pass or fail, from `result.json`.
2. `attempt.json` + `stages.log` (1 line) and no `result.json` → `FAILED_USERSPACE`, with the stage
   name.
3. `attempt.json`, no `stages.log` → `FAILED_BOOT`. This is the branch R2-11 says is missing: failure
   in the kernel or initramfs, the exact class the marker was supposed to catch. The host writes the
   record with the digest, the timeout and a required `photograph` field, and refuses to close the
   run until the path is filled in.
4. No `attempt.json` → `HARNESS_ERROR`.

**Why this is the right layer.** A `sysinit.target` unit cannot observe an initramfs failure (the
plan's own finding, R2-11), and neither can anything else inside the failing kernel. Only a writer
outside the machine, before the attempt, can cover that class, and only a stage log inside the
machine can split "kernel died" from "userspace died". Two layers, four outcomes, no branch left to
the operator's memory. The photograph stays the capture path for case 3 and is now a required field
in the record rather than an unrecorded habit.

### The inverted conditions and the unit logic

Beyond the Touch ID unit above, the inventory at `:271-291` has three conditions to check and one
duplicate:

- `bluefin-t2-touchbar-attach.service`: `ConditionPathExists=` on the t2bdrm DRM node. Correct as
  written, because udev creates the node and the unit does not. Keep.
- `bluefin-t2-firmware-import.service`: `ConditionPathExists=/boot/efi/kait2en/firmware/wifi`.
  Correct direction (the kit or the post-script writes the source; the unit reads it), but it must
  not use the unit's own output directory as the condition. Specify the source as a **marker the
  writer creates** (`/boot/efi/kait2en/firmware/.complete`) or, better, condition on
  `SHA256SUMS` existing, so a half-written payload cannot pass the condition.
- `bluefin-t2-firmware-import.path`: watches the same directory the service writes to. As written it
  can re-trigger on its own output. Specify: watch `PathExists=` on the *incoming* directory
  (`/boot/efi/kait2en/firmware/SHA256SUMS`), and make the service remove nothing; it copies to
  `/var/lib/firmware/brcm/` and writes `/var/lib/bluefin-t2/firmware.state`, which is outside the
  watched path.
- `bluefin-t2-first-login.service` (report) and the bind unit are the same event. One unit, one
  helper (see R2-9), unless the human gate keeps them separate; the engineering cost of two markers
  and two helpers for one event is the duplication Phase 1 L6 already rejected.

### The kargs mechanism

**Decision.** v1 ships the **13** arguments, as a named set, with no model exceptions, and Phase 1's
four-model class A needs none. A per-model karg is not expressible by any static mechanism on bootc
today, so class B, the Airs and the iMacs stay out until a runtime mechanism is designed and probed.

**Why, with the count corrected.** KAIT2EN's `ADD_ARGS` is ten entries
(`scripts/fedora/install-kernel-args.sh:69-78`), then two more are appended at `:120-122`
(`initcall_blacklist=…`, `module_blacklist=…`), so the live set is **12**, which `/proc/cmdline` on
the target confirms verbatim. `firmware_class.path=/var/lib/firmware` is **ours**, not KAIT2EN's: it
appears nowhere in the KAIT2EN tree (`grep -rn firmware_class` over `research/KaiT2en-Fedora` returns
nothing), and the kernel parameter is real and empty on the target
(`/sys/module/firmware_class/parameters/path` exists, prints empty). So the total is 13, not the
plan's "11 base args + firmware_class.path" (`:256`) and not the "expected 12-argument list" (`:431`).
Assert the named set, in order, with a diffable expected list, and delete the count. A count
assertion is the same defect the plan correctly rejected for the 18 objects (R2-5).

**Why no model needs an exception in class A.** The complete exception set upstream is
`iMac*` (drop `pcie_aspm=force`) and `MacBookPro16,1` (drop the AMDGPU and PCIe ASPM args), at
`install-kernel-args.sh:80-116`. No 13-inch model matches either branch. That is a fact about the
four models, not about one, which is why Phase 1's class claim survives.

**How a per-model karg would ever work, if someone wants it.** `kargs.d` is declarative and static:
`/usr/lib/bootc/kargs.d/*.toml` with `kargs = [...]`, applied at install and on upgrade while
preserving machine-local args (bootc docs, `building/kernel-arguments.md`). There is no
`match-product-name` key. The only paths are (a) ship the safe union, losing the ASPM benefit on the
models that need it; (b) a privileged first-boot writer that edits the deployment's local args and
reboots, guarded by the fact that bootc preserves machine-local kernel args across upgrades; or
(c) a per-model image variant, which multiplies the build matrix. Recommendation: (b) as the v2
design, with the probe being "does a machine-local arg survive `bootc upgrade`" on a throwaway
install. Until that probe exists, class B is gated by a mechanism, not by a model list, and the
design should say so rather than implying the gate is validation effort.

### ACPI overrides

**Decision.** v1 ignores ACPI entirely, as the plan says, and **v2 must not plan on
`rpm-ostree initramfs-etc --track`**, because that is an rpm-ostree mechanism and the target is a
bootc system.

**Why.** The plan's v2 route (`:317-319`, `:519-520`) is
`rpm-ostree initramfs-etc --track` plus `rpm-ostree initramfs --enable`, and the plan itself marks it
unverified. On a bootc image there is no rpm-ostree-managed initramfs pipeline: the initramfs is
built in the image (`19-initramfs.sh:7-9`), and bootc's documented per-machine surfaces are kernel
args and loader entries, not initramfs content. So the v2 route as written is not a route. The honest
options for per-machine ACPI tables are (a) bake the known tables for known models into the image,
which is exactly what a supported-model list makes safe, or (b) find a bootc-supported early-userspace
hook, which needs a probe and may not exist. v1 costs nothing either way: no model in class A is
recorded as needing an ACPI override.

**Cost of getting this wrong.** A v2 design that assumes the rpm-ostree route produces a plan whose
central mechanism does not exist on the platform, discovered at the point where a user's machine
needs it.

## Examined beyond the carry-forward list

### 1. The step sequence and its failure ordering

Order is correct where it matters and wrong in one place. The plan's order is 06 modules, 07
packages, 08 apps, 09 policy, 10 initramfs (`:213-249`), which is right: dracut must run after
everything that ships a dracut drop-in or a module. Bluefin's own order confirms the shape
(`build_files/shared/build.sh:28-68`: image-info, kernel+akmods, packages, overrides, extensions,
cleanup, workarounds, initramfs, tests, `bootc container lint` at `Containerfile:50`).

Five ways a step can pass while producing a broken image, and the fix for each:

| Green-but-broken path | Why it is silent | Fix locked above |
|---|---|---|
| kmod RPMs install for the wrong kver | nothing checks vermagic at install time | `Requires: kernel-core-uname-r` in the RPM (step 01), asserted in A1 Tier 0 |
| `depmod -a "$KERNEL"` with an empty or wrong `KERNEL` | depmod creates a directory tree and exits 0 | derive `KERNEL` from `rpm -q kernel-core --qf '%{VERSION}-%{RELEASE}.%{ARCH}'`, assert exactly one `/usr/lib/modules/*` entry |
| dracut omits a `force_drivers` module | dracut warns and continues | `lsinitrd` assertion inside `90-tests.sh` (step 07), not only in CI |
| `semodule -i` succeeded but the PAM feature did not | `authselect` failures on a non-Fedora base | grep the resulting `/etc/pam.d/system-auth` for `pam_fprintd.so` in `90-tests.sh` |
| apps installed but their typelibs/icons missing | GTK warnings at runtime, not build time | `ldd` closure test + `gtk4-demo`-free import test in Tier 0 |

One ordering defect: the plan puts `fc-cache -f`, `gtk-update-icon-cache` and `dconf update` inside
step 08 (`:231`), before step 09's policy install and before any dconf database the step 09 SELinux
work or the hub might add. Move the cache generation to step 05 in the locked sequence above, after
all files are in place, and assert the font is indexed (`fc-list | grep -i jetbrains`).

### 2. The 18-object set across four models

Verified by probe on the validated model: all 18 resolve via `modinfo -n` to
`/lib/modules/7.2.11-200.fc44.x86_64/extra/*.ko.xz`, and `dkms status` lists exactly 12 packages. The
plan's enumeration is right and R2-5's arithmetic correction is right.

Two corrections that matter to the assertion:

- **`t2gmux` does not load on MacBookPro16,2.** `lsmod` does not show it at all. The plan says it
  "loads and stays unbound" (`:191-193`, `:473-475`) and Tier 2 asserts the loaded set includes it.
  That assertion fails on the validated model. The honest per-model datum is: expected *absent from
  `lsmod`*, present in the image. Lock this into `models.d/MacBookPro16,2.toml`.
- **`hid_t2magicmouse` loads with no device bound** (refcount 0, no Magic Mouse paired). It is loaded
  but unbound, which is a third category the plan does not have. Three categories, not two:
  `expected_loaded`, `expected_absent`, `expected_unbound`.
- **`t2sep` is a latent 19th object.** `modules/t2sep/dkms.conf` exists in the KAIT2EN tree with
  `PACKAGE_NAME="t2sep"` but it is not among the 12 registered packages and `modinfo t2sep` reports
  "not found". The 18-object set is correct today *because it names objects*, not because it counts
  the tree. This is the strongest argument for the named-set style and should be recorded next to it.

Per-model differences, as far as evidence allows: none of the 18 is built per model. What differs is
binding, and the only differences this review can state with evidence are the two above plus
`hci_bcm4377`'s DMI board table gap for 15,4 (`research/findings/kait2en.md:437-446`). Everything
else must be *measured* on the second model rather than inferred, which is why the expectation file is
data and not prose.

### 3. Package and build split

Answered in the locked architecture: make it structural with a builder stage, keep the Tier 0
absence assertion as defence in depth, and add a filesystem assertion for the residue that an RPM
database cannot see. The plan's current claim ("Tier 0 asserts the build-only set is absent from the
committed image", `:421-424`) is necessary and not sufficient.

### 4. Test coverage

The four tiers survive this review with three repairs and one addition. Repairs: the `lsinitrd`
assertion moves inside the build; the `t2gmux` expectation is corrected; the kargs assertion becomes a
named set of 13. The addition: a rotation drill, run once per key rotation, not per release.

### 5. Build and boot performance, where it is a real constraint

- **Image size**: the builder stage costs nothing in the final image; the eight apps and the hub cost
  roughly 60–130 MB compressed, and the DSP profiles and fonts are small. Budget it: assert the
  compressed image delta against plain Bluefin stays under 250 MB in CI, and fail the build if it
  does not. The plan has no size budget at all.
- **Build minutes**: two pulls of the same base plus 10–25 minutes of Rust builds, so 45–70 minutes
  against the plan's 30–60 (`:89`). Acceptable; the constraint that matters is the next line.
- **Tier 2 wall clock**: the plan says 15–20 minutes per HIL cycle (`:487-488`), and its own Tier 2
  description includes `bootc install to-disk`, a first boot, an 18-object assertion, an import, a
  suspend cycle and a power-off (`:445-480`). Install alone is 10–30 minutes. The realistic number is
  35–55 minutes of wall clock plus operator attention at both ends. Phase 1 U3 said the cadence is
  unstaffable; this review supplies the number that makes the case. The harness should record
  per-stage wall clock to the stick so the cadence decision is made on data.

## Untested edges

These are the paths that no tier catches. Each is named with where it would belong.

1. **The `updates.img` post-script actually runs.** Only Tier 3 can prove it, and Tier 3 is the last
   gate before release. If it does not, the fix is a kickstart block and a new ISO, which is a full
   rebuild. (TD1.)
2. **A machine-local kernel arg surviving `bootc upgrade`.** Needs a throwaway install and two
   upgrades; belongs to the v2 per-model kargs probe. Nothing in v1 depends on it, and nothing tests
   it, so it will be discovered late.
3. **Key rotation end to end.** No tier rotates a key. The drill is defined above and is not in any
   tier's cadence.
4. **A second model.** Tier 2 runs one bench; class A's other three models are proven by argument,
   not by measurement. That is a stated Phase 1 decision and remains an untested edge, not a gap to
   close in v1.
5. **The kit on a machine with more than one internal disk, or a Fusion/APFS container.** The kit
   lists external disks only (`prepare-fedora-installer.sh:470-476`) and refuses internal ones, so
   this is probably fine, but nothing tests the case where macOS reports an external enclosure as
   `Internal`.
6. **`bootc switch` from a stock Bluefin that already has an NFS/container customization.** Route 2's
   rebase interaction with user-added deployments is unexamined.
7. **The report's `--json` schema across versions.** The hub and `result.json` depend on it; nothing
   tests that an older hub can read a newer report, which matters once the image updates underneath a
   user.
8. **Suspend with a USB HIL stick attached.** The Tier 2 suspend cycle runs with the results stick
   mounted; a real user's suspend does not. Minor, but it is the only suspend evidence the project
   will have.

## TASTE DECISIONS

Genuine close calls. Each goes to the human gate; evidence does not settle them.

### TD1: does the firmware crossing live in the kit's updates image, or in the ISO's kickstart?

*Real tradeoff:* the post-script inside `updates.img` rides the artifact the kit already writes and
already passes on the cmdline (`grub.cfg.in:12`), so a fix ships with a kit release and needs no ISO
rebuild; but it depends on an Anaconda feature (`/usr/share/anaconda/post-scripts/`) that is documented
and not proven in this tree, and if it does not work the fallback is a full ISO rebuild discovered at
the first Tier 3. The kickstart block at ISO build time is proven in this evidence base
(`iso-bluefin.toml:1-5`) and is a plain `%post`, but it moves the transfer code into the image release
cycle, where a one-line fix costs an ISO build and a Tier 3 run, and it risks interacting with BIB's
generated kickstart. My recommendation is the updates image first, the kickstart as the documented
fallback decided at the first ISO build, because the kit is the artifact that owns this payload and
because a fix should not wait on a 30–60 minute ISO build.

### TD2: single-sign, or dual-sign during a key rotation?

*Real tradeoff:* single-sign keeps the signing path one line and one key, which is what the design
chose (`:194-205`), and it is correct for the kernel because we do not hold the kernel key. Against it:
the moment the module key rotates, every user who has not enrolled the new key loses the modules on
the next upgrade, which is the Lockout case, and the only warning is a report line they may never run.
Dual-signing for two releases (`dual-sign.sh:15-22` is already in the tree for exactly this) costs a
second signature per module and a second key in CI, and it makes rotation boring. My recommendation is
dual-sign during an overlap of two releases, because rotation is a once-a-year event and a lockout is
forever, but this is the owner's risk appetite, not mine.

### TD3: does Tier 2 gate every image change, or every release?

*Real tradeoff:* per-image-change at daily cadence is what the plan promises (`:512-513`, `:554`) and
it is the guarantee that a bad kernel never reaches a user; at 35–55 minutes per cycle plus operator
attention at both ends, seven a week is a part-time job for the one person who also has to fix what it
finds, and a gate that cannot run is not a gate. Per-release gating is honest and it narrows the
window in which a bad daily build can reach a user to the release boundary, which is still narrower
than any peer project. My recommendation is per-release gating *plus* the CI checks, with the harness
recording wall clock so the number is measured rather than argued, but the calendar belongs to the
person holding the bench.

## USER CHALLENGES

Three premises this review believes are wrong. The human decides; the review did not stop for them.

### U1: "an unloadable input module makes the machine unrecoverable" is the wrong hazard model

**Assumption:** Constraint 5, "An unloadable input module makes the machine unrecoverable by its
owner" (`:81-83`), and the success criterion built on it (`:537-544`).
**Why it is wrong:** the Apple firmware provides the keyboard to GRUB, which is why the kit can
observe that GRUB gets keys but has no Ctrl-X or F10 (`auto-installer/grub.cfg.in:26-27`). So with
zero T2 modules loaded, the boot menu still works, the previous deployment is still selectable by
arrow keys and Enter, and rollback still recovers the machine. The genuinely unrecoverable case is
narrower and different: a *fresh* install with no previous deployment, and LUKS-encrypted root with no
way to enter the passphrase. That distinction changes the recovery documentation, the value of the
enrolment step, and how much the project should spend avoiding the hazard versus documenting the way
out of it.
**Cost of proceeding as written:** the docs teach "do not get here" instead of "here is the way out",
the enrolment screen is designed around fear rather than instructions, and the first user who does get
there has no page to read on a machine whose only channel is a dead keyboard.

### U2: "11 base args" and "the expected 12-argument list" cannot both be true, and neither is

**Assumption:** the kargs table row says "11 base args + `firmware_class.path`" (`:256`) and the Tier 0
assertion says "compared to the expected 12-argument list" (`:431`).
**Why it is wrong:** KAIT2EN appends twelve (`install-kernel-args.sh:69-78` plus `:120-122`), live
`/proc/cmdline` on the target shows twelve, and `firmware_class.path` is ours, not upstream's, so the
real total is thirteen. Both stated numbers are wrong, and the assertion is a count, which is the
exact style the plan correctly rejected for the 18 objects one page earlier.
**Cost of proceeding:** the first green build fails Tier 0 on an assertion that was never true, the
failure looks like a code defect, and the fastest fix that presents itself is dropping an argument.
Assert the named set or do not assert.

### U3: "15–20 minutes per HIL cycle" cannot cover the Tier 2 the plan describes

**Assumption:** Tier 2 costs 15–20 minutes (`:487-488`) and therefore one run per daily image change
is affordable (`:554`).
**Why it is wrong:** the plan's own Tier 2 includes a containerised whole-disk install, a first boot,
the 18-object assertion, a firmware import, a suspend cycle and a power-off (`:445-480`). The install
alone is 10–30 minutes, and the operator has to attach and detach the results stick at both ends.
Phase 1's U3 reached this conclusion from the staffing side; this review supplies the number from the
step list. A gate whose stated cost is a third of its real cost is a gate that will be skipped, and
skipped silently.
**Cost of proceeding:** the release guarantee is published, believed, and not actually enforced,
which is worse than publishing a weaker guarantee that is.
