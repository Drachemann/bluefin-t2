## Verdict

**This is a rigorously specified machine and an unspecified experience.** The plan knows what
every unit, module, karg and assertion does, to the line. It does not know what the user sees at
any point in the product's life. Nine of the thirteen user-visible subsystems have no state, no
message and no recovery path addressed to the person holding the laptop; the four that do
(firmware, the Touch Bar, the fingerprint, suspend) are each specified as a *mechanism* that
happens, not as a *thing the user is told*.

The sharpest way to say it: on the machine this product is for, the single most likely failure —
Wi-Fi with no Apple firmware — currently presents as **a missing icon**. The user reads that as
"Linux doesn't do Wi-Fi on this Mac". The product knows exactly what is wrong, knows the four
filenames, knows the path, and says none of it in a place the user will look.

Three consequences, all of them fixable inside v1's blast radius:

1. **The install ends in silence.** After a successful route-1 install the user has no surface
   that says what worked, what did not, and whether their machine is the supported one. The
   product's own thesis fails at the first login (`:532-535` measures up to a boot, not to a user
   knowing).
2. **Two surfaces contradict each other at the scariest moment.** The kit's own Secure Boot check
   tells the user to set "No Security" (`research/KaiT2en-Fedora/scripts/macos/prepare-fedora-installer.sh:93-100`)
   while the design commits to signing and MOK enrolment (`:107-109`). The kit is kept "verbatim"
   (`:342-345`), so both instructions ship.
3. **Two states that will happen a lot do not exist.** "This model is not supported" has no
   surface anywhere (the plan supports one model, `:110-111`). "This worked but you did not see
   it" has no surface either — every daemon that silently succeeds and every daemon that silently
   fails look identical.

**Overall design completeness: 3/10.** With the seven gaps below closed — which is one new
user-facing command, one first-login unit, one hub window, and three pieces of copy — this plan
is an 8/10 and the thesis becomes true.

## Experience gaps, ordered by user pain

Ordered by how many users hit it × how badly it lands. Each gap names what the user sees today,
what they should see, and the smallest change that closes it.

### G1 — First boot tells the user nothing, and cannot (every install, every user)

**Sees today.** A successful route-1 install ends, the USB comes out, the machine boots, GDM
appears, they log in. Nothing is said. If the firmware payload crossed (`:369-375`), Wi-Fi
appears a few seconds into the session because the import unit restarts NetworkManager (`:391-392`)
— which reads as a glitch, not as a successful import. If it did not cross, there is no Wi-Fi
device at all, and the only signal is a missing icon. Both cases are the same experience from the
user's side: nothing happened, and no one said anything.

**Should see.** One surface, once, at first login: this machine is a MacBookPro16,2; here is what
works; here is the one thing that does not and the four files that fix it.

**Why the plan's answer cannot work.** The plan's absence path is "a desktop notification from the
import unit, and `kait2en-firmware-status` reporting `absent`" (`:400-401`). Both are unreachable
at the moment they matter:

- The import unit is a **system** oneshot ordered `Before=network-online.target`,
  `Before=NetworkManager.service` (`:389-393`). It runs before any user session exists. A
  desktop notification fired from a system unit at that point reaches no session bus. KAIT2EN's
  equivalent is a live-environment unit gated on a runtime path
  (`research/findings/kait2en.md:386-389`), which is a different situation.
- `kait2en-firmware-status` requires a terminal and, more importantly, requires the user to
  already know the command exists. Nothing in the image, the kit output or the desktop names it.
  On a machine with no Wi-Fi, the user also cannot read the docs that would.

**Smallest change.** One user unit, `bluefin-t2-first-login.service`, first-login only via a
marker file, that opens a terminal window running the status surface **only when something is
not OK**, and exits on keypress. Two files plus the status command. On a fully-working machine
nothing opens — which is the correct empty state and is itself the trust signal.

**Evidence.** Plan `:400-401`, `:389-393`, `:369-375`; `research/findings/kait2en.md:393-412`
(the failure lives in `dmesg`, which is not a user surface), `:422-431`.

### G2 — The product gives two opposite Secure Boot instructions, and route 2 gives none (every user, at the most frightening moment)

**Sees today.** On the Mac, the kit checks the firmware policy and prints:
`Good: Secure Boot has been disabled.` or `Warning: Secure Boot is not disabled or could not be
verified.` followed by four steps ending `Set Secure Boot to No Security.`
(`research/KaiT2en-Fedora/scripts/macos/prepare-fedora-installer.sh:87-102`). The design says the
opposite: "Signing is committed for v1 … MOK enrolment happens from the live installer
environment before the installed system's first boot" (`:107-109`). The kit is kept verbatim
(`:342-345`), and its Secure Boot check is in neither the keep list nor the drop list — it is an
unassigned surface whose default is the wrong advice.

**Worse, route 2 has no Secure Boot story at all.** `mokutil` and MOK appear in the plan only in
route-1 and Tier-2 contexts (`:107-109`, `:537-544`, `:574-577`). Route 2 — `bootc switch` from
an existing Bluefin (`:361-365`) — is the only route for a machine whose macOS is gone
(`01-ceo.md:265-276`), and it has no enrolment step. On such a machine with Secure Boot on, our
signed modules do not verify against a MOK that does not exist, the input modules do not load, and
the machine comes up with no keyboard. That is Constraint 5's unrecoverable case (`:81-83`),
arrived at through the documented path.

**Should see.** One instruction per route, in the kit's own voice, that says what the product will
do and how to undo it: route 1 "Secure Boot stays on; the installer enrols a key; you will be
asked to confirm a code at the next boot"; route 2 "run `mokutil --import` now, while your
external keyboard is attached, and confirm at the next boot". The word "No Security" should not
appear anywhere in a product that signs.

**Smallest change.** Replace `check_startup_security`'s advice with two route-conditional text
blocks; add a three-line MOK step to route 2's documented procedure. Copy only — the enrolment
mechanism is Phase 3's.

**Evidence.** Plan `:107-109`, `:342-345`, `:361-365`, `:537-544`, `:574-577`, `:81-83`;
`research/findings/kait2en.md:35-36` (upstream ships nothing signed and says "No Security");
`research/KaiT2en-Fedora/scripts/macos/prepare-fedora-installer.sh:93-100`.

### G3 — "This model is not supported" does not exist as a state (every user not on a 16,2)

**Sees today.** The image installs on any T2 Mac. The plan supports exactly one model
(`:110-111`) and has a per-model expectation map only in prose — `t2gmux` loads and stays
unbound on a 16,2 (`:192-193`), which the plan calls "a named set with expected absentees". On a
`MacBookPro15,4` the image will install, some modules will bind, some will not, some apps will be
useless, and **nothing anywhere says whether this is expected**. Phase 1's challenge 1 is exactly
this (`01-ceo.md:250-263`); this review adds that it is a *surface* problem, not only a scope
problem.

**Should see.** A three-way verdict at first login, from DMI `product_name`: **validated**
(`MacBookPro16,2` — everything in the report is expected), **supported** (the 13-inch class —
"shares the module set, bar and DSP maps; `t2gmux` unbound is expected; send the report if X
fails"), **unknown** ("not validated on this model, here is the report to attach to an issue").
Plus the model table on the machine: `/usr/share/bluefin-t2/MODELS.md` (Phase 1's touch 5,
`01-ceo.md:163-164`, given a home here).

**Smallest change.** One `product_name` read in the status command, three message strings, one
markdown file in the image. No new mechanism, no per-model logic.

**Evidence.** Plan `:110-111`, `:192-193`, `:321-324`; `01-ceo.md:60-99` (the class argument this
surface makes readable to a user); `research/findings/kait2en.md:433-446` (three different keys
identify a model, and none of them is one number — the surface must not pretend otherwise).

### G4 — The Touch Bar is six undocumented gestures on a black strip with no escape hatch (every Touch Bar user, every day)

Assessed in full below ("The Touch Bar as an interface"). The gap in one line: the bar's default
state is *off* (`apps/t2-touchbar/README.md:4`), its six gestures are discoverable only by reading
a README (`:4-20`, `:47-50`), a daemon that fails to attach is indistinguishable from a design
choice (`:108-111`), and there is no in-product way to return to Apple's row.

**Sees today.** A black strip where the function keys used to be.
**Should see.** A taught first five minutes, a visible failure line, and a switch.
**Smallest change.** A first-run overlay drawn on the bar (three panels, ~10 s, once), the
`--status` output surfaced in the hub, and one hub toggle that disables the global user unit and
reboots into Apple's row.

### G5 — Six `T2 *` windows and two invisible commands, with no map and no place to look (every user, every day)

Assessed in full below ("The app-set surface").

**Sees today.** A GNOME app grid containing `T2 Fan Control`, `T2 SMC Control`, `T2 Power
Explorer`, `T2 Zone Power`, `T2 Power Tune`, `T2 Force Click` — and no explanation of which are
settings, which are diagnostics, which are one-shot, or which should never be opened twice. The
two tools that would answer "what is wrong" — `t2journal` and `t2remote` — ship with no desktop
entry at all, so the user never learns they exist.
**Should see.** One entry point, one overview, the tools behind it.
**Smallest change.** One hub window plus `NoDisplay=true` on the six desktop entries.

---

### G6 — Route 2 is one line of documentation for a multi-boot ordeal (a subset, badly)

**Sees today.** `sudo bootc switch ghcr.io/<org>/bluefin-t2:stable && sudo reboot`, described as
"one reboot on an external keyboard" (`:361-365`). What actually happens: the user is on a stock
Bluefin T2 machine that has no internal keyboard *at all* — so they are already on an external
keyboard for the entire session; after the reboot, before the modules load, they are on it again;
with Secure Boot on and no MOK (G2), they keep needing it indefinitely; and with no payload on any
ESP (the kit never ran), Wi-Fi never comes back (`:369-375`), so the machine that was going to
save them from external hardware now requires it permanently.

**Should see.** A route-2 page that opens with "have these on the desk: an external keyboard, a
USB stick with your firmware, the image reference" and then walks the reboot, naming what the
machine will look like at each stage and what to do if it is not.

**Smallest change.** One docs page, and the route table at `:358-365` extended with a
"keyboard needed until" column. No code.

**Evidence.** Plan `:358-365`, `:363-365`, `:369-375`; `01-ceo.md:265-276`; `research/findings/kait2en.md:35-36`.

---

### G7 — There is no recovery surface in the user's hands (every user, exactly when it matters)

**Sees today.** The plan's recovery contract is written for the author: "never install to the
internal disk; Option-boot back; previous deployment pinned" (`:479-480`), plus "Rollback from the
boot menu restores a working machine" (`:553`). A user whose machine has no initramfs keyboard
cannot read a plan document. Nothing ships a recovery page, and the one command that would help —
Apple's row instead of the bar, previous deployment, firmware from a USB — is not in the image as
a discoverable action.

**Should see.** The same first-login surface, reachable again at any time (`bluefin-t2` with no
arguments), carrying a "what to do if this does not work" block: Option-boot, pick the previous
deployment, and for each of the three most likely failures the exact command.

**Smallest change.** One section in the same window G1 builds. Zero new files if G1 lands first.

## The install journey, walked end to end

One paragraph per step. Steps 2-5 run on macOS; 6-7 are the installer; 8-10 are the first
session. What is missing is named per step.

**1. Choosing a route.** The user arrives with a T2 Mac and a claim ("installs itself"). Nothing
in the plan gives them the first question: *does this machine still boot macOS?* The route table
exists in the design document (`:358-365`) and will not exist in anything the user reads. Route 1
is described as requiring no external hardware and route 2 as requiring "one reboot on an external
keyboard" (`:361-365`), and the fact that route 2 needs a keyboard for the whole session and
possibly forever (G6) is not on the table. **Missing: the decision tree, and the precondition
("macOS must still boot") stated where a stranger meets it** (`01-ceo.md:265-276`).

**2. Pre-flight on macOS.** The kit starts with a Secure Boot check that tells the user to turn
Security off (`prepare-fedora-installer.sh:87-102`), contradicting the product (G2). Then it picks
an edition and a target disk from menus (`:311-314`, `:343-353`) — retargeted to our single ISO
(`:346`), so that menu collapses, which is correct and is a real improvement in the flow. The
disk menu shows a list of `diskN` identifiers with no capacity, no model and no "this is not your
boot disk" reassurance at the point of choosing; the reassurance arrives one step later as a typed
confirmation, `ERASE diskN` (`:595-605`).

**3. The typed wipe confirmation.** This is the best-designed moment in the whole journey: a
phrase that cannot be typed by accident, a refusal that names why (`:480`), and re-prompting that
tells the user Ctrl-C is how to back out (`:604-605`). It earns trust because it is specific about
its own danger. Nothing before it sets the stakes, though: the user has not yet been told what
they will gain, only what they will lose.

**4. Firmware capture.** `ioreg` reads what macOS asked the firmware loader for
(`research/findings/kait2en.md:396-401`), and if nothing comes back the kit dies with a message
that is a model for the rest of the product: **name the cause, name the fix, name the escape
hatch** — "Enable Wi-Fi, reboot macOS, and retry, or use `--firmware-dir`"
(`prepare-fedora-installer.sh:167`). Two things are missing. The user is never told *what was
captured*; the chip, the board name and the four filenames are all known at this moment and this
is the cheapest possible point to catch a wrong capture (Phase 1's touch 4, `01-ceo.md:161-162`).
And nothing tells them these files are per-machine and cannot be recovered later — the one fact
that decides whether they wipe macOS next week.

**5. Write, verify, carry, and the last thing they read.** The ISO is written, re-validated
(`prepare-fedora-installer.sh:626-637`), the ESP is edited with free-space pre-checking and
`cmp` verification of every file (`:655-676`), and then the user gets four lines of next steps
ending: *"Sign in to Fedora. The KaiT2en installation will continue automatically in a terminal."*
(`:683-689`). For route 1 that sentence describes a guided installer this design deletes
(`:353-356`, `:347-351`). **The product's final instruction on the Mac promises a phase-2 terminal
installer that does not exist**, and it says "Fedora installation" where the screen will say
Bluefin T2. This is the single cheapest trust fix in the entire review: three lines of copy.

**6. Booting the USB and the installer.** The win is real and should be stated in the product's
own words: the ESP carries a second initramfs with five modules (`:333-336`,
`research/findings/kait2en.md:19-21`), so the internal keyboard and trackpad work in the installer
environment — the thing `t2-atomic` cannot do and the reason this project exists. Two small
surprises are unaddressed. The live environment has `t2hid` and `t2touchbar_bl` but no Touch Bar
daemon, so the bar is whatever the firmware row shows, for the whole install; the user has never
been told the bar will be inert until first login. And "removes the Anaconda addon entirely"
(`:347-351`) drops the only thing that ever wrote firmware into the target sysroot — R2-3 is still
open (`:646`, `:680-684`) and Phase 1 escalated it as a launch blocker (`01-ceo.md:178`). On the
user's side, that open item is the difference between "Wi-Fi works after install" and G1.

**7. Where is the Secure Boot enrolment screen?** `:107-109` says enrolment happens "from the live
installer environment before the installed system's first boot", and `:574-577` says the wiring
comes after the ISO exists. So the plan commits to a screen the user will see, in a place it has
not designed, whose worst outcome is the unrecoverable no-keyboard state (`:81-83`, `:537-544`).
**Missing: what that screen says, what the user does, and what happens if they walk away from it.**
The copy is design work, not cryptography, and it is the one place where a bad sentence bricks a
laptop.

**8. First boot.** Plymouth theme, GDM branding (`:262-263`), then GDM. Three per-user units may
or may not run here: `kait2en-touchid-bind.service` is conditioned on
`ConditionPathExists=%h/.config/kait2en/touchid-bound` (`:284`), while the prose describes it as
"runs once per user (marker `~/.config/kait2en/touchid-bound`)" (`:302-305`) — the condition reads
as inverted against the marker semantics, and R2-9 is still listed open at `:648`. The mechanism
is Phase 3's. The experience consequence is mine: **if either per-user unit fails, the failure is
silent and the user's only evidence is that the fingerprint prompt never appears and the bar does
not respond.** Neither failure has a message, and neither is distinguished from "this machine does
not do that".

**9. First login and the firmware import.** If the payload crossed, `kait2en-firmware-import.service`
runs before networking, performs unbind → remove → install → rebind (`:376-388`), and restarts
NetworkManager (`:391-392`). The user sees Wi-Fi populate several seconds into the session, with no
explanation. If the payload did not cross, nothing happens and nothing says so (G1). Either way the
exceptional behaviour here — the deliberate SC-1 bounded-risk `unbind` of a live PCI function
(`:381-386`) — is the kind of thing that should be *reported*, not just performed, because it is
the step the author himself got wrong twice (R1-11 → R2-10, `:818-820`).

**10. The first week, which the plan does not cover.** The first kernel bump (`bootc upgrade`,
`:551-552`), the first suspend in a bag (`:547-548`), the first time the fingerprint prompt does
not appear. The plan's success criteria stop at boot (`:532-535`) and its cadence assumes an
operator (`01-ceo.md:278-290`). From the user's side, the product's job begins exactly where the
plan's criteria end. That is the gap the validation report closes, and it is why G1's surface must
stay reachable, not be a one-shot.

## The app-set surface

**What ships.** Step `08-t2-apps.sh` builds eight things from the pinned submodule as RPMs
(`:227-231`), plus the `t2remote` helper. Counted honestly against the source tree, that is
**six GUI windows, two terminal-only tools and one daemon** — and the split matters, because
the two tools a user would need *when something is wrong* are the two with no window at all:

| Shipped | Kind | Desktop entry `Name` / `Comment` (source) |
|---|---|---|
| `t2-fan-control` | GTK4/libadwaita window + `t2-fancontrol.service` | "T2 Fan Control" — Control T2 Mac fans on Linux (`apps/t2-fan-control/org.t2fancontrol.gtk.desktop`) |
| `t2-smc-control` | GTK window + `t2-smc-gaugingd.service` | "T2 SMC Control" — SMC temperatures and battery charge limit |
| `t2-power-explorer` | GTK window | "T2 Power Explorer" — Inspect kernel device topology and runtime power state |
| `t2-zone-power` | GTK window + `t2-zonepowerd.service` | "T2 Zone Power" — Watch the SMC power zones of T2 Macs on Linux |
| `t2-power-tune` | Python GTK app + helper + `kait2en-power-tune.service` | "T2 Power Tune" — Tune PCIe ASPM and system power-saving settings |
| `t2-force-click` | GTK window + `t2-force-click.service` | "T2 Force Click" — Configure trackpad click and force click pressure and actions |
| `t2-journal` | **CLI only** (`t2journal`), no window | none — installs binaries only (`t2-services/t2-journal/Makefile:6,23-27`) |
| `kait2en-touchbar` | **daemon**, no window | none |
| `t2remote` | **CLI helper** | none |

So a fresh install adds **six icons** to the app grid, all named `T2 <noun>`, all categorised
`System` / `Settings` / `HardwareSettings` / `Monitor` — which is to say the categories assert
"these are all the same kind of thing" while the things are not the same kind of thing at all.
Fan Control is a settings surface you revisit. Zone Power is a live monitor. Power Explorer is a
developer's device tree. Journal is a log reader for a debugging session that **never appears in
the app grid at all**. Power Tune is a
fire-and-forget tuner whose README opens with a **reset procedure** and a **recovery when the
system does not boot** (`apps/t2-power-tune/README.md:1-15`) — a tool so sharp it documents its own
rescue. Force Click is a preference you set once and forget.

There is no tray icon anywhere (no `StatusNotifier`/`ksni`/appindicator dependency in any app) and
no hub: I checked. Four background daemons (fan control, smc gauging, zone power, force click)
plus three more services (power-tune, touchid, t2-remote) run with no aggregate state visible
anywhere.

**The design problem, stated exactly.** The user's real question on a fresh install is not "where
are the fan controls". It is *"is this machine working, and what did I get?"* The windows cannot
answer that question, because the answer is a property of the machine, not of any one app. The
plan's only answer to that question is a hardware-in-the-loop rig (`:445-480`) that belongs to the
author. This is the same gap as G1, seen from the app grid instead of from the desktop.

### Recommendation: one hub at the front, not eight peers

Ship **one new app**, `bluefin-t2`, as the single visible entry point. Keep every existing app
as it is — do not rewrite, do not merge, do not re-brand — and set `NoDisplay=true` on the
six desktop entries that exist. The hub is an `AdwNavigationSplitView` with one Overview page and nine rows:

```
+------------------------------------------------------------------+
```

Each of the nine sidebar rows opens the existing app (Overview is the only new page; Display,
Input, Thermal, Power, Battery, Audio, Diagnostics and Recovery are *links*, and where a row maps
to an existing app it launches that app unchanged). Two exceptions deserve their own row because
they currently have no window at all: **Display (Touch Bar)** gets a small page with
`kait2en-touchbar --status` output, the layer/timeout facts from `touchbar.toml`, and the
"Use Apple's Touch Bar row" switch; **Recovery** is G7's block of exact commands.

Why this and not the alternatives:

- **Eight visible peers (do nothing):** zero work, and the user never gets the overview that is
  the product's whole second half. The windows are not the product; they are the product's
  knobs.
- **Merge the windows into one libadwaita app (rewrite):** the honest full version, and it costs a
  rewrite of six app crates whose widgets are not library-ised. Violates P5 (explicit over
  clever) for no user-visible gain over the hub: the hub already gives one entry point and one
  Overview.
- **Hub that embeds the six windows as pages (partial merge):** middle cost, middle reward, and it
  commits the hub to tracking six upstream apps' internals across rebases — the worst
  maintenance shape available for a project already on a rebase treadmill (`:579-581`).

The hub is ~200 lines of Rust plus one desktop file and one icon, all reusing `adwaita` and
`gtk4` already in the build. It is the cheapest way to turn "a folder of tools I was given" into "one
machine that tells me its state". It also gives the product a name in the app grid —
`bluefin-t2`, the shipping name (`:114-116`) — which is the first place a user will ever see it.

**Naming note.** The plan's *new* binaries carry the KAIT2EN name: `kait2en-firmware-status`
(`:400-401`), `kait2en-import-firmware` (`:397-398`), `kait2en-firmware-import.{service,path}`
(`:285-286`), `kait2en-nm-bridge.service` (`:287`), `kait2en-touchid-bind.service` (`:284`). The
plan is careful that the *distribution* is `bluefin-t2` because `TRADEMARK.md` requires permission
for the name (`:492-494`, `:114-116`). Inherited units keep inherited names — that is factual
reference. New surfaces we author are a naming choice, and they should be ours:
`bluefin-t2-firmware-import.*`, `bluefin-t2-first-login.service`, `bluefin-t2`. Otherwise the
product is named one thing on the ISO and another in `systemctl list-units`.

## The Touch Bar as an interface

**What the plan adopts.** KAIT2EN's bar, wholesale: the config and udev rule into the image
(`:261`), the daemon as a user unit (`:283`), and a success criterion that says only "Touch Bar
renders the KAIT2EN bar" (`:549-550`). The craft underneath is genuinely good and this review does
not want it changed:

- dark-first, black until touched or Fn (`apps/t2-touchbar/README.md:4`);
- a timeout that **learns** — 5 s floor, 30 s ceiling, decaying when the extension goes unused
  (`README.md:53-56`, `etc/kait2en/touchbar.toml:3-4`);
- three fixed layers plus up to four personal keys, created with commented examples on first run
  (`README.md:9-40`);
- swipes that work on the *dark* bar without waking it: two-finger volume, three-finger
  brightness, esc in its slot (`README.md:47-50`, `touchbar.toml:26-31`);
- haptics through `t2_trackpad_actuator`, with per-phase control (`README.md:70-72`);
- a fingerprint prompt drawn on the bar, keys vanishing, arrow nudging at the sensor
  (`README.md:54-59`) — and no Apple artwork, which is the kind of constraint-honouring detail
  that earns trust;
- glyphs dimmed in software to follow the keyboard backlight, with a readable floor
  (`README.md:73-78`, `touchbar.toml:18`).

That is a product someone cared about. What the plan adopts is the craft and not the *onboarding*,
and the onboarding is where this design fails.

**Discoverability: six gestures, zero affordances.** To use the bar the user must discover: touch
to wake; Fn to wake; short Fn to switch to the last layer; 600 ms Fn hold to switch rows
(`README.md:18-21`); two-finger swipe on the dark bar for volume; three-finger swipe on the dark
bar for brightness; two-finger swipe on the lit bar to ring through layers (`README.md:47-50`).
None of this is on the screen, because the bar *is* the screen and it is off. On macOS the
equivalent surface had persistent labelled controls and a system-wide convention; here the
convention is a README the user does not have, on a machine with no Wi-Fi. The measured result
will be: users tap the black strip, nothing happens, they conclude the bar is broken — which is
exactly the "worked yesterday" bug report the product cannot afford.

**Failure visibility: the failure looks like a feature.** `kait2en-touchbar-attach.service` is
preset-enabled and conditioned on the t2bdrm device (`:282`). The daemon itself is a *global user*
unit (`:283`) and needs the `kait2en-touchbar` group — a per-user `usermod` that cannot happen at
build time and that the design does not have a mechanism for (R2-16, `:646-648`, `:806-814`). When
either fails, the README's own description of the disabled state is what the user sees: *"The
attach service then leaves the firmware row in place at boot"* (`README.md:108-111`). So the
broken state is **a working-looking Apple row** — indistinguishable from a deliberate design
choice, with no message anywhere. The plan's only assertion is Tier 2's "Touch Bar present and
usable as the desktop user" (`:476-477`), which is a test, not a surface.

**What happens when it does not work.** There is a real escape hatch, documented in the upstream
README and nowhere in the plan: `sudo systemctl --global disable kait2en-touchbar.service`, reboot,
and Apple's row returns (`README.md:105-111`). The user cannot reach it with no Wi-Fi and no
terminal, and the product never mentions it. The same is true of the two diagnostic commands that
exist — `kait2en-touchbar --status` and `--reset-learning` (`README.md:114-120`).

**Score: 5/10.** Craft 9, discoverability 2, failure visibility 1, recovery 2.

**What would make it a 10.** Three additions, none of them touching the bar's craft:

1. **A first-run lesson drawn on the bar itself.** On first login only, the daemon renders three
   panels that light up for ~4 s each and label the gestures in the product's own voice: *"Swipe
   here for volume"* over the dark bar; *"Hold Fn for function keys"* over the F-key row; *"Tap for
   media"* over the media row. The bar is a display; the cheapest onboarding is to use it. It
   should be dismissible on the first touch, and never shown twice.
2. **A visible failure line.** If the daemon starts but cannot attach (group missing, device
   absent, unit disabled), it says so **on the bar**, in one line, for the first 30 s of the
   session: *"Touch Bar not active — you are not in the `kait2en-touchbar` group. [fix]"*. A
   surface that fails must fail where the user is looking.
3. **A switch, in the hub's Display page, that does exactly what the README's disable command
   does**, with a reboot. "Use Apple's Touch Bar row" is a legitimate preference, not a
   workaround, and offering it removes the fear of trying the bar at all.

## The validation report

Phase 1's T1 asks whether the user-side report ships in v1 (`01-ceo.md:205-212`). This section
takes the "ship it" branch as the working assumption and specifies the artifact, because the
artifact is the part that was missing. If the human gate says v1 does not ship it, everything else
in this review still stands — the report is the largest single gap, not a dependency of the rest.

### The one insight that makes it cheap

The plan already names its assertions: the 18-object set with expected absentees (`:192-193`), no
`firmware load failed` in `dmesg`, Wi-Fi associated, bar usable as the desktop user, `fprintd-list`
non-empty, fingerprint offered at lock screen, `systemctl --failed` empty, one suspend/resume
cycle, DSP sink present (`:473-478`). Those are exactly the assertions a user's machine can make
about itself. **One assertion set, two front ends:** the HIL rig writes `result.json` to the
`K2B-HIL` stick (`:445-480`), and the user's machine writes the same schema to stdout. Same code,
two audiences — which is also what makes the report testable in Tier 0 without hardware, and
truthful on first use because the author has been running it for weeks.

### Shape

- **Name:** `bluefin-t2 report` (the shipping name, `:114-116`). Not `kait2en-*` (see the naming
  note above). Sub-commands that the first-login surface and the hub both call: `report` (human),
  `report --markdown` (bug report), `report --json` (same schema as `result.json`).
- **Exit codes:** `0` everything expected; `1` something is not working; `2` this model is not in
  the validated set. Exit codes matter because the first-login unit decides whether to open a
  window by running it, not by duplicating the logic.
- **No network. No telemetry. No upload. Ever.** The `--markdown` file is placed in the user's
  home and its path printed. The product asks the user to paste it; it never sends it. This is not
  a preference — a hardware-enablement tool that exfiltrates a machine's device state before it has
  Wi-Fi is a trust failure with no upside.
- **One screen, no scrolling at 80×25.** Fixed line budget: header 1, working 1 + N, not-working
  1 + N, expected-absent 1 + N, footer 1.
- **Truthful about what it cannot know.** Anything it cannot test (an untested model, a
  Bluetooth path that the kernel's DMI table does not list, `research/findings/kait2en.md:442-446`)
  is reported as *untested*, never as *working*.

Not a dashboard. Not telemetry. Not a health score. A user does not need a percentage; they need
the one line that says what is broken and the one command that fixes it. Subtraction default: if a
line does not change what the user does next, it goes.

## TASTE DECISIONS

Five close calls. Each with the real tradeoff; none is settled by the evidence.

### T1 — Does the first-login surface open a window, or stay passive?

*Real tradeoff:* a window that appears unbidden on first login is the pattern the goodwill
reservoir tells you to avoid — "splash screens, forced tours, interstitials" (`SKILL.md:621`), and
on a working machine it is pure noise. But on a machine where Wi-Fi is missing, a passive surface
(hub icon only) means the user's first 30 minutes are spent concluding the product is broken; the
whole point of the second half of the thesis is that the machine speaks first. The split I would
ship is "opens only when something is wrong, never on a working machine" — but that makes the
product's behaviour depend on state the author cannot test on his own (his machine works), and a
first-login window that misfires on a good machine is a worse first impression than silence.

### T2 — One hub hiding the apps, or eight visible entries?

*Real tradeoff:* one hub is the coherent answer to "what does this machine have", and `NoDisplay`
is the only way to get there without a rewrite — and it also removes six discoverable entry
points for a power user who wants `T2 Fan Control` in two clicks, and diverges from every
screenshot and doc that KAIT2EN users already know. Eight visible entries cost nothing and keep
upstream familiarity, at the price of the product never having a front door and never having a
name in the app grid. This is the difference between shipping a machine and shipping a toolbox.

### T3 — Does the Touch Bar default to dark-first, or always-lit for the first week?

*Real tradeoff:* dark-first is the inherited craft and it exists for a reason — the bar is off most
of the time, which is where the power saving comes from (`README.md:4-6`), and the learned timeout
is the most thoughtful interaction in the whole inherited design. Against it: dark-first is also
the reason the bar will read as broken to every new user, and a product whose second-most-visible
hardware feature looks dead on first boot has an onboarding problem that no amount of learned
timeout fixes. Options: keep dark-first and teach it (T5); default to always-lit for N days then
hand over; or make "always lit" a first-run choice presented on the bar itself. Not my call: it
trades power against first impressions on a laptop, which is the author's to weigh.

### T4 — What happens on a model that is not the validated one?

*Real tradeoff:* a hard refusal (refuse to boot / refuse to install on anything but
`MacBookPro16,2`) is the most honest gate and the most hostile outcome — it turns away a 15,4 owner
whose machine would very likely work, and it is exactly the "one-machine port" Phase 1 rejected
(`01-ceo.md:250-263`). A soft verdict (report + `MODELS.md` + "untested") makes every early user a
data point, and it also means the product can be installed on machines it will half-support, with
the evidence for that being a markdown file the user may never read. The middle option — soft
verdict at first login, hard gate only on models in a positive deny list (the dGPU and non-Touch-Bar
classes, `01-ceo.md:64-66`) — is coherent but needs a deny list somebody has to own.

### T5 — Does the shipped app set get the product's name?

*Real tradeoff:* renaming six windows to `bluefin-t2 · Fan control` makes the product coherent
and trademark-clean in one move, and it forks every app's branding from upstream, breaks every
existing screenshot and doc, and creates a rebase cost on a tree already consumed as a pinned
submodule (`:579-581`). Keeping `T2 *` keeps the submodule honest and leaves the product's name
appearing nowhere a user looks, which is a strange outcome for a distribution with a
`TRADEMARK.md`-driven naming decision. The hub-only compromise (product name on the one new
surface, upstream names untouched) is what I would ship, and it is a compromise, not a resolution.

## USER CHALLENGES

Three premises I believe are wrong. The human decides.

### U1 — "The install is the product" measures the wrong half

**Assumption:** the product's moment of truth is a clean install with no external hardware, which
is why success criterion 1 is scoped to route 1 (`:145-147`, `:534-535`).
**Why it is wrong:** the install is the moment of *delight*; the product's moment of truth is the
first week — the first `bootc upgrade` (`:551-552`), the first suspend in a bag, the first time
the fingerprint prompt does not appear. The plan's criteria stop at a successful boot, and nothing
in the plan is addressed to the person at step 10 of the journey. A user who installs perfectly
and then loses Wi-Fi permanently on the first kernel bump has had a worse experience than one who
installed with an external keyboard and never noticed.
**Cost of proceeding:** the project will be judged on the demo and will be reviewed on the
support thread. The report (G1/T1) is the only artifact that converts the second into evidence,
which is why it is the highest-value item in this review, not a taste decision.

### U2 — "The kit is kept verbatim" is not free reuse

**Assumption:** the kit's capture, write, verify and carry steps can be kept as they are, with
only the target configs retargeted (`:342-346`).
**Why it is wrong:** the kit is a *script with a voice*, and its voice belongs to the old product.
It tells the user to disable Secure Boot (`prepare-fedora-installer.sh:93-100`) where the design
enrols a key (`:107-109`); it closes by promising "The KaiT2en installation will continue
automatically in a terminal" (`:683-689`), a guided installer this design deletes (`:347-356`); and
it names Fedora where the screen will say Bluefin T2. Its Secure Boot check is in neither the keep
list nor the drop list, so it ships by default. Mechanical verbatim reuse of a user-facing script
carries a non-verbatim product.
**Cost of proceeding:** the first artefact this project ever asks a stranger to run gives them two
contradictory security instructions and a promise it does not keep — and the stranger is, by
definition, about to wipe a laptop on that advice.

### U3 — A terminal status command is being treated as a user surface

**Assumption:** the plan's answer to "what happened to my machine" is `kait2en-firmware-status`
plus a notification (`:400-401`), and Phase 1's remedy for the other twelve silent subsystems was
"one status surface for the whole T2 layer" (`01-ceo.md:182`, `:154-156`).
**Why it is wrong:** a command is not a surface. It has no discoverability (nothing names it), no
reachable path on the exact machine state it exists for (no Wi-Fi means no docs), and no place in
the desktop. The notification that was supposed to compensate fires from a system unit before any
session exists (`:389-393`), so it reaches nobody. This is not a consistency problem between
subsystems; it is the product being unable to speak at all.
**Cost of proceeding:** twelve of thirteen subsystems keep failing silently from the user's side,
and the one that does speak does so into a terminal the user has no reason to open — on a machine
whose headline failure is the loss of the network that would explain it.
